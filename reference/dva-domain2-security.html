The golden rule of Domain 2 If an option involves storing an access key, secret key, or password anywhere — that option is almost always WRONG. AWS's answer is always: make sure no permanent credential exists at all. Instead: IAM roles (temporary credentials) and Secrets Manager / KMS. This one rule alone will win you half of Domain 2.

1. IAM — policy evaluation (a guaranteed question)

Picture a security guard at a building. Three cases: (1) If a list says "do not let this person in" — they cannot enter, even if another list has their name. (2) If a list says "let them in" — they enter. (3) If they appear on no list at all — they also cannot enter. That is the whole of IAM.

OrderRuleResult
1Explicit DENY — is there a Deny anywhere?DENIED. Always wins. No Allow can override it.
2Explicit ALLOW — is there an Allow?ALLOWED.
3Nothing written at all (implicit deny)DENIED. The default is always deny.

Memory phrase: "Explicit Deny > Explicit Allow > Implicit Deny". This is near-guaranteed on the exam — only the wording changes.

Parts of an IAM policy

  • Effect — Allow or Deny.
  • Action — which operation, e.g. s3:GetObject, dynamodb:Query.
  • Resource — on what, as an ARN.
  • Principal — who (only in resource-based policies).
  • Condition — when, e.g. aws:SourceIp, aws:MultiFactorAuthPresent.
Identity-based vs Resource-based Identity-based policies attach to a user/role: "what can this person do". Resource-based policies attach to the thing itself (S3 bucket policy, Lambda resource policy): "who may touch this resource" — this is where Principal appears. Cross-account access usually needs BOTH — a common exam trap.

2. STS and roles — the right way to do credentials

  • sts:AssumeRole — obtains temporary credentials (15 minutes to 12 hours). This is AWS's preferred answer to every "how do I grant access" question.
  • On EC2: attach a role via an instance profile. The code does nothing — the SDK picks up credentials automatically.
  • On Lambda: the execution role. Same idea.
  • On ECS: a task role (per-task).
  • Cross-account: create a role in the other account that trusts yours, then AssumeRole. NEVER share access keys.
  • SDK credential chain order: environment variables → shared credentials file (~/.aws/credentials) → IAM role (instance/task/execution). The exam sometimes asks this order.

3. Cognito — User Pool vs Identity Pool

This is the most common confusion on the exam. A hotel analogy makes it clear:

 User PoolIdentity Pool (Federated Identities)
Hotel analogy The reception desk — who are you? Show ID, register, sign in. The room key card — which rooms/pool/gym you may now access.
Job AUTHENTICATION — sign-up, sign-in, MFA, password reset. Issues a JWT token. AUTHORIZATION — issues temporary AWS credentials so the user can call S3/DynamoDB directly.
Trigger words "sign up / sign in", "user directory", "MFA", "social login (Google/Facebook)" "give users direct access to AWS resources", "temporary AWS credentials"

They're often used together: the User Pool authenticates → its token goes to the Identity Pool → the Identity Pool returns AWS credentials. If a question asks for both, the answer is both.

4. KMS and encryption

KMS numbers
  • KMS directly encrypts only up to 4 KB. ⭐ Bigger data? Use envelope encryption — call GenerateDataKey, encrypt your large data with that data key, and store the encrypted data key alongside. This is a certain exam question.
  • Automatic key rotation: every 1 year (automatic for AWS-managed keys; you enable it for customer-managed keys). The old key is kept, so old data still decrypts.
  • Key deletion: a 7 to 30 day waiting period (default 30). Never immediate.

Encryption types — through S3

  • SSE-S3 — AWS manages the keys, you do nothing. Simplest. (Now on by default in S3.)
  • SSE-KMS — KMS keys, giving you an audit trail (CloudTrail shows who decrypted and when) and control over the key. "Audit" or "control over the keys" = SSE-KMS.
  • SSE-C — you supply your key on every request; AWS never stores it. HTTPS required.
  • Client-side encryption — you encrypt in your own code BEFORE sending to AWS. "AWS must never see the plaintext" = client-side.

Encryption in transit = TLS/HTTPS. Encryption at rest = protected on disk. Questions often require both.

5. Secrets Manager vs Parameter Store — a favourite comparison

 Secrets ManagerSSM Parameter Store
Automatic rotationYES — built in, with native RDS integrationNO (you'd build it with Lambda)
CostCosts money (per secret per month)Standard tier is FREE
Best forDatabase passwords, API keys that must rotateConfig values, feature flags, non-secret settings
Exam trigger⭐ "automatically rotate" = always Secrets Manager⭐ "MOST cost-effective" + config = Parameter Store
Exam English — read carefully These two questions look almost identical but have different answers:
• "store database credentials that must be rotated automatically" → Secrets Manager
• "store configuration values in the MOST cost-effective way" → Parameter Store
The difference is two words. This is exactly why finding the qualifying word matters so much.
