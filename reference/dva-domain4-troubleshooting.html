The whole domain in one sentence CloudWatch tells you THAT there is a problem. X-Ray tells you WHERE the problem is. That one line solves half of Domain 4. If the question asks "which service is slow / where is the bottleneck" — the answer is always X-Ray. If it asks "alert me when errors rise" — CloudWatch.

1. CloudWatch — three different things

Think of CloudWatch as a hospital: Logs = the patient's full written record. Metrics = the numbers on the monitor (heart rate, temperature). Alarms = the bell that rings when a number crosses a danger threshold.

ThingWhat it isExam trigger
CloudWatch Logs Text logs. Log group → log stream → log events. Lambda sends these automatically (if the execution role has permission). "view application output", "find errors"
CloudWatch Metrics Numbers over time. AWS provides many; create your own with PutMetricData. "track a value", "custom metric"
CloudWatch Alarms A threshold on a metric. States: OK / ALARM / INSUFFICIENT_DATA. Notifies SNS. "notify when", "alert if"
Logs Insights A query language over logs — search and analyse them. ⭐ "query the logs", "analyze log data"
Metric Filters Finds a pattern inside logs and turns it into a METRIC (e.g. count of "ERROR"), which you can then alarm on. ⭐ "alert based on something in the logs"
CloudWatch numbers
  • Standard metrics: 5-minute intervals. Detailed monitoring: 1-minute (costs extra). "1-minute granularity" = enable detailed monitoring.
  • Custom metrics: 1-minute standard, 1-second high-resolution.
  • Log retention: never expires by default — which is why costs creep up. Exam trigger: "reduce log storage costs" = set a retention period.
  • ⚠️ Memory and disk usage are NOT default EC2 metrics. You must install the CloudWatch Agent for those. A common exam question.

2. AWS X-Ray — distributed tracing

Analogy: a parcel travels through 5 cities and arrives 3 days late. CloudWatch tells you "the parcel is late". X-Ray gives you a timestamp at every city so you can see it sat in Lahore for 2 days. That's distributed tracing — the request's whole journey, with time spent at each service.

  • Segment — one service's work. Subsegment — a smaller piece inside it (e.g. a database call).
  • Service map — a visual diagram of which service calls which, and where errors are.
  • ⭐ Annotations vs Metadata — the exam asks this. Annotations are INDEXED, so you can search/filter on them. Metadata is NOT indexed — it's just extra detail. "Filter traces by..." = annotations. (Task statement 4.2.4.)
  • Sampling — X-Ray doesn't trace every request (too expensive). Default: the first request each second + 5% of the rest. "Reduce tracing costs" = adjust the sampling rule.
  • To enable on Lambda: turn on Active Tracing + the execution role needs AWSXRayDaemonWriteAccess. On EC2: you must run the X-Ray daemon.

Exam English — DAX vs ElastiCache Both are caches and both can front DynamoDB. The deciding phrase is usually "minimal code changes". DAX is API-compatible with DynamoDB — you only change the endpoint. ElastiCache requires you to write the cache-check and cache-write logic yourself. So: "minimal/least code changes" + DynamoDB = DAX. Session storage, or a general cache for any database = ElastiCache.

A CloudFront exam favourite

Cache based on request headers (task statement 4.3.5). To serve different content to different users (mobile vs desktop, or different languages), you must include that header in the cache key — otherwise everyone gets the same cached copy. But including more headers lowers the cache hit rate. The exam asks about this tradeoff.

4. Performance and cost optimization

  • Lambda memory tuning — CPU scales with memory. Often more memory makes the function faster AND cheaper (because duration drops so much). This is counter-intuitive and the exam tests it. Tool: AWS Lambda Power Tuning.
  • SDK retries with exponential backoff — on throttling errors, the SDK retries with growing gaps. "ThrottlingException" or "503" in a question = exponential backoff with jitter. (Task statement 1.1.13.)
  • Connection reuse — in Lambda, create SDK clients and DB connections OUTSIDE the handler (global scope) so warm invocations reuse them. This is the most common Lambda performance question.
  • RDS Proxy — connection pooling for Lambda + RDS. Thousands of concurrent Lambdas will exhaust the database's connections. "Too many connections" = RDS Proxy.
  • SNS subscription filter policies (task statement 4.3.4) — send a subscriber only the messages it cares about, rather than sending everything and filtering in the consumer. Cuts both cost and load.
  • S3 lifecycle rules — automatically move old data to cheaper storage classes (Standard → IA → Glacier). "MOST cost-effective" + "old data" = a lifecycle policy.
Error codes — the exam asks these
  • 4xx = client error (your request is bad). 5xx = server error (problem on AWS's side).
  • 400 ThrottlingException / ProvisionedThroughputExceededException — too many requests. Fix: exponential backoff, or raise capacity.
  • 403 AccessDenied — an IAM permissions problem.
  • 429 TooManyRequests — API Gateway throttling.
  • 502 Bad Gateway — usually Lambda returned a malformed response to API Gateway (proxy integration requires statusCode and body).
  • 504 Gateway Timeout — API Gateway's 29-second timeout was exceeded.
