Sessions vs JWT: how login state is remembered

HTTP forgets you after every request. So how does the server remember you're logged in? Two approaches.

~8 min One concept: sessions vs tokens Win: explain how login is remembered

30-second warm-up (recall stateless servers)

From memory: in the load balancers lesson (03) we said servers should be stateless. What did that mean?
Stateless = any server can handle any request, because a server doesn't keep your data in its own local memory. Login state lives somewhere shared (like Redis/DB) or on the client itself. Today we look at exactly that: where login state should live.
click to reveal — say it first
If you remember one thing Session = the server keeps your login state and gives you an ID cookie (it must look that ID up on every request). JWT = the whole login info lives with the client in a signed token (the server just verifies the signature — no lookup). One keeps a list to check; the other writes everything on the band.

The problem: HTTP forgets you

HTTP is stateless. Every request stands alone — the server doesn't remember who logged in a second ago. So how does it know across two requests that "this is the same person who just logged in"? Both approaches solve exactly this.

The story: a coat-check ticket vs a concert wristband

You walk into a fancy restaurant and hand your coat to the cloakroom counter. They give you a small numbered ticket — nothing written on it except a number. When you come back, you show the ticket, the staff look that number up in their list, and fetch your coat. The ticket itself is empty — the real info is held at the counter.

Now picture a concert. At the entrance they fasten a signed, tamper-proof wristband on you with everything written on it: your zone, whether you're VIP, how long it's valid. Inside, any staff member just checks the band is genuine (hologram/signature) and lets you through — no list to look anything up in. All the info is on the band.

  • Coat-check ticket = session cookie. An empty ID; the real data sits at the server's counter (DB/Redis). The server must look it up every time.
  • Concert wristband = JWT. The info is on the band itself, cryptographically signed. Staff just verify it's genuine — no lookup.
Django bridge Django's default session framework is exactly the coat-check way: request.session data is stored on the server (SESSION_ENGINE decides where — a DB table by default, or Redis with the cache engine), and the browser only gets a sessionid cookie. On every request the middleware looks that ID up. On the API side, djangorestframework-simplejwt gives you JWTs: the client sends Authorization: Bearer <token>, the server verifies the signature — no session table hit for DRF views. That's why mobile apps and SPAs often use JWT: no cookie/CSRF dance, no shared session store needed, and it scales easily across many stateless API servers (exactly the stateless thinking from lesson 03).

Quick check: with a JWT, why doesn't the server have to hit the DB on every request?
Because the user's info is inside the token and the token is signed. The server only verifies the signature (with its secret key) to be sure the token wasn't tampered with — then it trusts the info inside. No lookup.

The tradeoff — name it in interviews Sessions are easy to revoke but need storage + a lookup on every request (and shared storage when you have many servers). JWTs scale nicely without a lookup but are hard to revoke before they expire — a stolen token keeps working until expiry. So keep JWTs small, keep their expiry short, and never put secrets in them (the payload is only signed, not encrypted — anyone can read it). Need instant logout? Either use sessions, or pair JWTs with a short expiry + refresh tokens (or a small server-side blocklist).
A team moved their API to JWTs. Now logging a user out immediately from the admin side is surprisingly hard. What's the root reason?
You have a dozen stateless API servers behind a load balancer and want to avoid a DB lookup on every request. What fits better for login state?
Your win today HTTP forgets you, so login state either lives on the server (session = coat-check ticket + a lookup per request, easy to revoke) or on the client in a signed token (JWT = wristband, no lookup, scales well, but hard to revoke and must stay small + secret-free). In Django: the default session framework vs simplejwt for APIs. Saying "sessions are easy to revoke, JWTs are easy to scale" in an interview is a clean senior signal.
