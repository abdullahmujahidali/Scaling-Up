DynamoDB: Query vs Scan, and LSI vs GSI

DynamoDB is the second-biggest topic in Domain 1. The exam almost always asks two things: why Query instead of Scan, and LSI or GSI for a new index. One rule answers both.

~9 min One concept: find rows by key, never by searching Win: two guaranteed exam questions
Recall from A2: what's Lambda's max timeout, and API Gateway's?
Lambda 15 minutes (900 seconds). API Gateway 29 seconds. Today's topic connects: a slow query can time out a Lambda — but the real problem is usually how you queried, not the timeout.

If you remember one thing In DynamoDB you always fetch by key, never by searching. Query = go straight to it by key (fast, cheap). Scan = read the entire table looking for it (slow, expensive). On the exam, "the application is slow" or "costs are high" + a Scan = the answer is use Query, and if there's no key on that attribute, create a GSI.

The story: a bookshelf

Imagine a library with 50,000 books. You want "Harry Potter". Two ways:

Way 1 (Scan): start at the first shelf and pick up every book to read its title until you find it. 50,000 books. You will find it — but it takes all day, and longer as the library grows.

Way 2 (Query): look in the catalogue under "H". Go straight to shelf 12 and take the book. Ten seconds.

In DynamoDB, a Scan is exactly Way 1 — and you pay for every book you picked up, not just the one you wanted. That's why Scan is both slow and expensive. Now the meaning of an index: the index is the catalogue. If the catalogue is only by title and you want to search by author, you need a new catalogue — that's a GSI.

OperationWhat it doesCost and speed
GetItem Fetches exactly one item by its full key. Fastest. Cheapest
Query Fetches all items for a partition key (optionally filtered by sort key). ⭐ The exam's preferred answer. Fast and cheap — you pay only for what it read
Scan Reads the whole table, then filters. ⚠️ The filter applies after reading — so a filter does NOT reduce cost. Slow and expensive
Trap — the "just add a filter" option AWS often offers: "add a FilterExpression to the Scan so less data is returned." This is wrong. A FilterExpression applies after the read — DynamoDB still reads the whole table and you still pay the full cost. Only the amount sent over the network shrinks. Speed and cost are unchanged. The option exists precisely because the logic sounds right but isn't.

LSI vs GSI — the hook for this pair

The memory hook L = Local = Locked. An LSI can only be created while the table is being created — never afterwards. Its partition key stays the same; only the sort key differs.

G = Global = Go ahead any time. A GSI can be created whenever, even on a table that's been in production for years, and any attribute can be its key.

⭐ Exam shortcut: if the question says "existing table", "already in production", or "the table already contains data" → the answer is GSI, because an LSI is no longer possible.
The DynamoDB numbers the exam asks for
  • Item size: max 400 KB. Bigger than that → store the file in S3 and keep only the pointer in DynamoDB. ⭐ Asked often.
  • Query/Scan result: max 1 MB per call — beyond that you must paginate.
  • LSI: 5 per table, only at table creation. GSI: 20 per table, any time.
  • Capacity: On-demand (unknown or very spiky traffic) vs Provisioned (predictable traffic — cheaper). "Unpredictable" or "spiky" in the question = On-demand.
  • A strongly consistent read costs 2× and is not possible on a GSI at all. The default is eventually consistent.
Exam English — words in DynamoDB questions "throttled" / "ProvisionedThroughputExceededException" = you ran out of capacity. "hot partition" = all traffic hitting one partition key (answer: choose a key with more variety). "eventually consistent" = the answer may be slightly stale. "single-digit millisecond" = DynamoDB's normal speed; if the question says "microsecond", the answer is DAX.

An application runs a Scan on a DynamoDB table with 40 million items to find orders by customerId. Latency is high and costs are rising. The table is already in production and its partition key is orderId. Which solution will reduce latency and cost the MOST?

Domain 1 · Development · the numbers

An application needs to store user-uploaded documents in DynamoDB. Each document is between 2 MB and 8 MB. Fast queries on metadata (name, date, owner) are also required. Which design meets the requirement?

Bridge to your Django work This is exactly what you see in Django every day. When you run Order.objects.filter(customer_id=5) and there's no database index on customer_id, Postgres reads the whole table — a "sequential scan". You add db_index=True, run the migration, and it's instantly fast. A DynamoDB GSI is exactly Django's db_index=True — a new path to that column. And the "Scan + filter" trap is exactly like pulling the full queryset into Python and filtering with a list comprehension — it works, but the database already did all the work. The only difference is that DynamoDB charges you for that work, so the mistake hurts more visibly.
From memory: the table is in production and you need to query a new attribute — LSI or GSI? Why? And the max DynamoDB item size?
GSI — because L = Local = Locked: an LSI can only be created with the table, never after. The table already exists, so the LSI option is automatically dead. Max item = 400 KB.
