The GIL: why Python threads don't split the work

The first "why does Python behave like that?" — and the one interviewers love to poke.

If you remember one thing The GIL is a single lock that lets only ONE thread run Python code at a time. So spinning up 8 threads to crunch numbers 8× faster… doesn't work in normal Python. But for waiting-heavy work (network, disk), threads help a lot.

The story: one talking stick in a meeting

Picture a meeting room with a rule: you may only speak if you're holding the talking stick. There's exactly one stick. Ten people can be in the room, but only the one holding the stick actually talks; everyone else waits their turn.

In Python:

  • The talking stick = the GIL (Global Interpreter Lock).
  • The people = your threads.
  • Talking = running Python code.

So even on an 8-core machine, your 8 Python threads pass one stick around — only one runs Python at any instant. That's the whole idea, and it explains a surprising amount.

The key split: CPU-bound vs I/O-bound work

Whether threads help depends entirely on what your code is doing. Two kinds of work:

Kind of workExampleDo threads help?
CPU-bound (talking non-stop)crunching numbers, image resize, parsing huge dataNo. All need the stick — they queue.
I/O-bound (waiting a lot)calling an API, querying the DB, reading a fileYes. While one waits, it drops the stick.

Why I/O-bound is different: when a thread is just waiting for a network reply or the database, it isn't talking — so it puts the stick down. Another thread grabs it and does useful work during that wait. The GIL barely gets in the way. This is the crucial insight.

Django bridge — this matters daily A typical Django request spends most of its time waiting — on the database, on cache, on an external API. That's I/O-bound. So the thread-based workers in Gunicorn/uWSGI genuinely help: while request A waits on Postgres, its thread drops the stick and request B runs. But the moment you do heavy CPU work in a request (generating a big PDF, resizing images, crunching a report), the GIL bites — those can't run in parallel across threads, and they'll block your workers. That's your cue to move CPU work to a separate process (Celery worker) instead of a thread.
Quick check: you have a function doing heavy math. Will running it in 4 threads make it ~4× faster in normal Python? Why / why not?
No. Heavy math is CPU-bound — every thread needs the GIL (the stick) to run Python, so they take turns, not run together. You'd get roughly the same speed (or slightly worse from switching overhead). To actually use 4 cores, use 4 processes.

So how do you actually use all your cores?

If threads can't, what can? Multiple processes. Each process gets its own Python and its own stick — so 4 processes really do run on 4 cores at once.

  • Threads — great for I/O-bound work (lots of waiting). One stick, shared.
  • Processes (e.g. multiprocessing, Celery workers, Gunicorn workers) — great for CPU-bound work. Each has its own stick → true parallelism.
2026 update — the GIL is becoming optional (know this for interviews) Since Python 3.13 there's an experimental free-threaded build with the GIL removed, and in Python 3.14 (Oct 2025) it became officially supported (still not the default).2 The plan is a multi-year transition toward GIL-free by default (~2028–2030).3 So "Python can't do CPU parallelism with threads" is becoming "…in the default build, for now." Saying that in an interview shows you're current.

Your win today The GIL = one talking stick; only one thread runs Python at a time. So threads don't speed up CPU-bound work (use processes for that) but do help I/O-bound work (the waiting thread drops the stick). This one idea explains Gunicorn workers, when to reach for Celery, and why "just add threads" sometimes does nothing. And you know the 2026 twist: free-threaded Python is arriving.
