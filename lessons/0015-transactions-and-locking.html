If you remember one thing A transaction groups several database steps into one all-or-nothing unit — they all happen, or none do. Locking stops two transactions from stepping on each other at the same time.

Part 1 · Transactions — all or nothing

Story: transferring $100 from Ali to Sara is two steps: subtract $100 from Ali, add $100 to Sara. Imagine the power cuts out between the two steps — Ali lost $100 and Sara got nothing. Money vanished. A transaction says: "treat these two steps as one. If both can't complete, undo everything." No half-done state, ever.

This is the A in ACID — Atomicity (all-or-nothing), which you first met back in the SQL lesson. Now you see why it matters.

Django bridge Django gives you this directly: with transaction.atomic(): wraps a block so if anything inside raises, the whole block rolls back — nothing is saved. Your money-transfer view should always be inside atomic(). Without it, a crash mid-way leaves your data in a broken half-state. This is one line that prevents a whole category of disasters. 
from django.db import transaction

with transaction.atomic():          # all-or-nothing
    ali.balance  -= 100
    ali.save()
    sara.balance += 100
    sara.save()                     # crash anywhere → both undone

Part 2 · The race condition — two people, one seat

Transactions handle crashes. But there's a sneakier problem: two things happening at the exact same time.

Story: one concert seat left. Two buyers click "buy" at the same instant. Both requests read "1 seat available," both think "great, it's free!", both write "0 seats, sold." You just sold one seat twice. That's a race condition — the result depends on who got there first, and nobody did anything obviously wrong.

The fix: locking

A lock says "while I'm working on this row, nobody else can touch it — they must wait." So Buyer A locks the seat, checks it, buys it, releases. Buyer B was forced to wait, and when they get in, they see "0 left" and are correctly refused. One seat, one buyer.

Django bridge — the actual fix select_for_update() inside an atomic() block locks the rows you read until the transaction ends. The second request blocks until the first finishes, then sees the updated value. This is the pattern for "decrement inventory / claim a seat / debit a balance" safely under concurrency. 
with transaction.atomic():
    seat = Seat.objects.select_for_update().get(id=seat_id)  # 🔒 locks the row
    if seat.available:
        seat.available = False
        seat.save()      # Buyer B waits here until we're done, then sees it's gone
Quick check: what's a race condition, and what tool prevents it?
Two operations running at the same time that read-then-write the same data, producing a wrong result (e.g. selling one seat twice). Prevent it with a lock — one must wait until the other finishes (in Django: select_for_update() inside atomic()).

The tradeoff — name it Locks make things correct but can hurt speed: while one transaction holds a lock, others wait. Lock too much or too long and you get slowdowns or even deadlocks (two transactions each waiting on the other, stuck forever). So lock the smallest thing for the shortest time. Correctness vs throughput — a real tradeoff to name out loud.
Your "redeem coupon" endpoint occasionally lets the same one-time coupon be used twice when clicked rapidly. Root cause and fix?
A money-transfer function subtracts from one account and adds to another. A crash between the two steps must not lose money. What do you wrap it in?
Your win today A transaction makes several steps all-or-nothing (Django's atomic()) — survives crashes. A lock stops two concurrent operations from corrupting the same row (select_for_update()) — survives race conditions. Together they're how you build anything with money, inventory, or seats without disaster. This is deep, real, interview-and-job depth.
