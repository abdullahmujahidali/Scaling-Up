CloudWatch, X-Ray and CloudTrail: which tool answers which question

All three are "observing" tools, so the exam swaps them as distractors. The way to keep them apart is easy: each answers a different question — WHAT, WHERE, and WHO.

If you remember one thing CloudWatch = WHAT is happening (metrics, logs, alarms — CPU at 90%, errors rising).
X-Ray = WHERE the time is going (the request's full journey — which service is slow).
CloudTrail = WHO did it (a record of API calls — who deleted the bucket).

"who" or "audit" in a question = CloudTrail. "which service is slow" = X-Ray. Everything else = CloudWatch.

The story: a hospital

  • CloudWatch = the patient monitor. Heart rate, temperature, oxygen — numbers ticking on a screen. If the heart rate goes above 120, an alarm sounds. It tells you what is wrong, not why.
  • X-Ray = the actual scan. To find where the pain comes from, you look inside. X-Ray shows a request's whole journey — API Gateway to Lambda, Lambda to DynamoDB — and how long each hop took. So when three services are involved and you don't know which is slow, the answer is X-Ray.
  • CloudTrail = the visitor register. Every door records who entered, when, and what they did. When the question is "who changed this medication?", you read the register. It's the audit record.

Trap — memory and disk are NOT default metrics By default EC2 sends CPU, network and disk I/O to CloudWatch — but not memory (RAM) or disk space. AWS cannot see inside the instance. Those require installing the CloudWatch Agent. The exam asks it like this: "the team wants an alarm on memory usage" — and the answer isn't "create an alarm", it's "install the CloudWatch Agent first". A favourite trap.
Domain 4 error codes — memorise these
  • 4xx = the client's fault (your request was bad). 5xx = the server's fault (AWS or your code).
  • 429 / ThrottlingException = you exceeded a rate limit. ⭐ The answer is always: retry with exponential backoff and jitter.
  • 502 Bad Gateway = Lambda returned a malformed response (usually the wrong response format).
  • 504 Gateway Timeout = API Gateway's 29 seconds ran out. (The A2 trap — the answer is going async.)
  • 403 = not permitted (IAM). 401 = not authenticated at all.
  • CloudWatch Logs retention: defaults to "Never expire" — so they stay forever and keep costing money. The cost-reduction answer: set a retention period.
Exam English — Domain 4 words "bottleneck" = the one place slowing the whole system (the narrow neck of a bottle). "latency" = delay. "throughput" = how much work gets done per unit time. "trace" = a request's full journey. "instrument the code" = add a tracing/monitoring SDK to it. "exponential backoff" = double the wait after each failure (1s, 2s, 4s, 8s). "jitter" = a small random variation in that wait, so all clients don't retry at the same instant.

Bridge to your Django work You already use all three; only the names differ. CloudWatch Logs = your Django log file / Sentry. X-Ray = Django Debug Toolbar or an APM (New Relic/Datadog) — the thing that tells you 600 ms of an 800 ms request went to the database. You've done the N+1 query lesson (0011) — X-Ray hunts exactly that problem across a distributed system. And CloudTrail has no Django equivalent, because it isn't your app's logs — it's the register of actions taken on the AWS account, like the django-admin-log table but for the whole infrastructure.
