Load balancers: the host at the door

How one entry point spreads traffic across many servers. The move behind "just add more servers."

If you remember one thing A load balancer is one front door that spreads incoming requests across many servers — so no single server gets crushed, and if one dies, traffic just goes to the others.

The story: a busy restaurant

A packed restaurant has one host at the door and many waiters inside. Diners don't wander in and pick a waiter — they'd all crowd the same one. Instead, the host stands at the entrance and sends each new group to whichever waiter has room.

That host is a load balancer. The waiters are your servers. Three things the host does, without you thinking about it:

  • Spreads the crowd — no single waiter (server) gets overwhelmed while others sit idle.
  • Skips the sick waiter — if a waiter goes home ill, the host just stops seating people there. (No more requests to a dead server.)
  • Removes the single choke point — you're no longer betting the whole night on one waiter.

The big idea it unlocks: horizontal scaling

There are two ways to handle more traffic:

  • Vertical scaling — buy your one waiter a bigger brain and faster legs (a bigger, pricier server). Works for a while, then you hit a ceiling.
  • Horizontal scaling — just hire more waiters (add more cheap servers behind the load balancer). This is what lets systems grow almost without limit.

Load balancers are what make horizontal scaling possible — the host is what lets you add a tenth waiter without chaos.

The one rule that makes it work: stateless servers Here's the catch. If waiter #2 is the only one who remembers your order, and the host sends your next request to waiter #5, you're stuck. So servers must be stateless — they keep no personal memory of you. Anything that must be remembered (like your login session) goes into a shared place all servers can read, like a database or a shared cache. (This is a very common interview "gotcha" — sessions must live outside the app servers.)
Django bridge Run Django on 3 servers behind a load balancer and you hit exactly this. If you use Django's default local-memory session storage, a user logged in on server 1 looks logged-out when the balancer routes them to server 2. The fix is what stateless means in practice: move sessions to a shared store — the database or Redis (SESSION_ENGINE). Same idea as the story: shared memory, not per-waiter memory.
Quick check: why must servers behind a load balancer be "stateless"?
Because the balancer may send your next request to a different server. If one server privately remembers your session, another won't know it. So shared state (sessions, etc.) must live in a place all servers can reach — a database or shared cache.

One nuance: Layer 4 vs Layer 7 (light touch)

You'll hear these two terms. Keep it simple:

  • Layer 4 — the host seats you by only glancing at the envelope: where you came from and which door (IP addresses and ports). Fast, doesn't read the message inside.
  • Layer 7 — the host actually reads your request ("table for the dessert menu?") and routes based on the content (the URL, cookies). More flexible, but more work.

For now, just remember: Layer 4 = route by the envelope (fast). Layer 7 = read the letter and route smartly (flexible).

The catch (name it in interviews) The load balancer is now itself a single point of failure — if the host collapses, nobody gets seated. Real systems fix this by running a second load balancer as backup (remember failover from 2b — active-passive!). It can also become a bottleneck if under-resourced. Naming this tradeoff is the senior move.

Your win today A load balancer is the host at the door: it spreads traffic, skips dead servers, and unlocks horizontal scaling (more cheap servers, not one huge one). The price of admission: servers must be stateless, with shared state in a database or cache. This is the backbone of nearly every "Design X" answer.
