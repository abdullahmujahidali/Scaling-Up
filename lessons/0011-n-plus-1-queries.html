The N+1 trap: the bug quietly killing your Django app

Invisible in code, brutal in production. The most common ORM performance bug there is.

~9 min One concept: N+1 queries Win: spot & fix N+1 in Django

30-second warm-up (recall SQL vs NoSQL)

From memory: give the one-line difference between SQL and NoSQL, and the "default" rule of thumb.
SQL = strict tables + joins + ACID; NoSQL = flexible shapes that scale huge with eventual consistency. Rule of thumb: SQL by default, NoSQL for a specific reason (scale, flexible schema, special access pattern).

If you remember one thing N+1 = you run 1 query to get a list, then 1 more query for each item in that list. 1 + N. Fine for 5 items, a disaster for 5,000. The fix is telling the ORM to fetch related data up front.

The story: a waiter with a bad system

A table of 50 diners each ordered a drink. A smart waiter asks all 50 at once (or checks one list) — one trip to the kitchen. A bad waiter takes one order, walks to the kitchen, comes back, takes the next, walks again… 50 separate trips plus the first one to seat them. That's 1 + 50 = 51 trips for what should've been 1 or 2.

Your database is the kitchen. Each "trip" is a query. The bad waiter is the N+1 problem — and Django's ORM makes it very easy to write by accident, because the extra trips are hidden.

Why it hides so well

Django querysets are lazy — they don't hit the database until you actually use the data. So this looks totally innocent:

books = Book.objects.all()          # 1 query
for book in books:
    print(book.author.name)         # +1 query EACH loop → N more

That book.author.name quietly fires a fresh query every single loop to fetch the author. 100 books = 101 queries. Nothing in the code looks slow — that's the trap.

The fix: fetch related data up front

Django gives you two tools to tell the ORM "grab the related stuff in the same trip":

ToolUse forHow it works
select_relatedForeignKey / OneToOne (the "one" side)Does a SQL JOIN — one query
prefetch_relatedManyToMany / reverse FK (the "many" side)A second query, then joins in Python — two queries total
books = Book.objects.select_related("author").all()   # 1 query, JOINed
for book in books:
    print(book.author.name)                            # no extra queries 🎉
Django bridge — how to actually catch it Install django-debug-toolbar (local) — it shows the query count per page. See "247 queries" on a list page? Almost always N+1. The fix is nearly always adding select_related (for ForeignKeys) or prefetch_related (for many-relations) to the queryset. This single habit is one of the biggest real-world speedups you can ship.
Quick check: select_related vs prefetch_related — which is for a ForeignKey, and how many queries does it use?
select_related is for ForeignKey/OneToOne — it does a SQL JOIN in one query. (prefetch_related is for many-relations and uses two queries.)

Your win today N+1 = 1 query for the list + 1 per item (the bad waiter's many trips), hidden by lazy querysets. Catch it with query counts (debug toolbar); fix it with select_related (ForeignKey → JOIN, 1 query) or prefetch_related (many → 2 queries). This is the depth that separates "the code runs" from "the code scales."
