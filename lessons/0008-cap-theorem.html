CAP theorem: pick two when the network breaks

The famous tradeoff — and it ties together consistency and availability you already know.

~8 min One concept: CAP Win: explain why you can't have it all

From memory: strong vs eventual consistency — one line each.
Strong — every read immediately sees the latest write (copies update synchronously). Eventual — reads see it after a short delay (copies update asynchronously). We're about to see why you sometimes can't choose strong.

If you remember one thing When the network between your servers breaks (a "partition"), you must choose: stay Consistent OR stay Available — you can't have both in that moment. That's the entire CAP theorem.

The three letters

  • C — Consistency: every read gets the latest write (or an error). No stale data.
  • A — Availability: every request gets a response (even if it's slightly old). Never "down."
  • P — Partition tolerance: the system keeps working even when the network between servers is cut.

CAP says: in a distributed system you can only fully guarantee two of these three at once.

The story: two shop branches, phone line cut

You run a shop with two branches that normally sync inventory over a phone line. One day the phone line goes dead (that's a partition — the network split). A customer walks into Branch B and asks: "Do you have item X?" Branch B is now stuck with a choice:

  • Stay consistent (refuse): "I can't confirm without calling Branch A, and the line's dead — so I won't answer." Correct, but unhelpful. You gave up Availability.
  • Stay available (guess): "Sure, we have it!" — based on possibly-stale info. Helpful, but might be wrong. You gave up Consistency.

There's no third option that's both correct and answers, while the line is down. That's CAP in one scene.

The real-world twist: P isn't optional Networks will fail — cables cut, packets drop. So partition tolerance (P) is mandatory in any real distributed system. That means the actual choice is always just C vs A when a partition hits. "Pick 2 of 3" is really "P is forced, now pick C or A."

Django bridge A single Postgres isn't distributed, so CAP doesn't bite — you get strong consistency, no partitions to worry about. But the moment you scale out (read replicas, a distributed cache, a multi-region database), you're choosing. Postgres with sync replication leans CP (it'll block/refuse rather than serve stale). A system like Cassandra or DynamoDB leans AP (always answers, eventual consistency). Now you know why those databases behave so differently — it's a CAP choice baked in.
Quick check: why is "partition tolerance" not really optional in a real system?
Because networks genuinely fail (cables, dropped packets) — you can't prevent partitions. So a real distributed system must tolerate them, which forces the true choice down to C vs A during a partition.

Your win today CAP: when the network splits, you pick Consistency (refuse rather than be wrong → CP) or Availability (answer, maybe stale → AP). Partition tolerance is forced, so it's really C-vs-A. This is the tradeoff behind "why is this database like that" — and naming CP vs AP in an interview is a strong senior signal.
