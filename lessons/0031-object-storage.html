Object storage (S3): don't keep big files in your database

Images, videos, PDFs, backups — keep them in a warehouse (S3), and keep only the ticket (URL) in your database.

~8 min One concept: object storage Win: know where files really belong

30-second warm-up (recall the CDN)

From memory: what does a CDN do, and what kind of thing does it serve close to the user?
A CDN keeps copies of your static files (images, JS, CSS, videos) on edge servers around the world, so they're served from close to the user — fast, and less load on your server. Today we look at where those files actually live — the answer is object storage, and the CDN sits in front of it.
click to reveal — say it first
If you remember one thing Don't store big files (images, videos, PDFs, backups) inside your database. Put them in object storage (S3), which is built to hold billions of files cheaply, and store only the URL/key in your database. A database is for structured, queryable data — not blobs.

The story: the cloakroom and your heavy suitcase

You're walking into a meeting room that's small, expensive, and crowded — only people and papers should come inside. You've got a heavy suitcase. Two options:

  • Drag the suitcase inside: the meeting room fills up, moving around gets hard, everyone slows down. Less room for the next meeting too. That's storing the file inside the database.
  • Leave it at the cloakroom / warehouse: hand the suitcase over at the counter, get back a small ticket in return. The meeting room stays empty and fast. When you want the suitcase, you show the ticket. That's storing the file in object storage and keeping only the ticket (URL) in your database.

The warehouse is great at exactly one thing: holding billions of boxes cheaply, each with its own ticket. The meeting room is great at one thing: small, clean, queryable things. Let each do its own job.

Django bridge In Django you use django-storages plus S3. Your FileField/ImageField now points at S3 instead of local disk — user uploads land in the warehouse, and the database column stores only the key/path (not the bytes). collectstatic can also push to S3, with CloudFront (a CDN) sitting in front of the bucket to serve everything fast. You never put file bytes in a Postgres column: rows bloat, backups get huge, SELECT * slows down, and RAM is wasted — Postgres is for small, indexed, queryable rows, not a 200MB video blob. For a secure direct upload use a presigned URL: your backend mints a short-lived signed URL and the browser uploads straight to S3 — big files never pass through your Django server.
Quick check: a user uploaded a profile picture. What goes into the database row?
Only the URL or key (like avatars/u123.jpg), not the image bytes. The actual image bytes live in S3; the app serves/links to that URL when needed (often via a CDN).

The tradeoff — name it in interviews Object storage isn't free: it's separate infrastructure (one more thing to configure and secure), and some operations can be eventually consistent — right after you write or delete a file, not every node may see it consistently. In exchange you get storage for files that's dramatically cheaper and more scalable. In an interview, say: "blobs go to S3, only the URL goes in the database — I accept a bit of eventual consistency because the cost and scale win is huge."

Your win today Big files go to object storage (S3) — billions of files, cheap, each with its own URL, often served via a CDN. Only the URL/key goes in the database, never the bytes. In Django: django-storages + S3 for uploads and collectstatic, presigned URLs for secure direct uploads. Tradeoff: separate infra and a little eventual consistency — but far cheaper and more scalable for files. Now you know where files really live.
