Consistent hashing: add a server without moving every key

A smarter way to spread data across servers so scaling up or down doesn't cause a cache stampede.

~8 min One concept: the hash ring Win: scale a cache cluster smoothly

30-second warm-up (recall sharding)

From memory: what does sharding do, and what "maps" a key to its shard?
Sharding splits one big dataset into smaller pieces (shards) on separate servers so no single machine holds everything. The simplest way to map a key to its shard is hash(key) % N — hash the key, then take modulo the server count. Today we'll see why that % N is a hidden problem.

If you remember one thing Picture servers and keys placed around a circle (a ring); each key belongs to the next server clockwise. Add or remove a server and only the keys near that one spot move — everything else stays put. That's how it avoids the massive reshuffle of hash(key) % N.

The problem: modulo breaks everything

Suppose you have 4 cache servers and you use hash(key) % 4 to decide which server holds which key. Now you add a 5th server for performance. The formula becomes hash(key) % 5. The problem: % 4 and % 5 give a different answer for almost every key.

That means nearly every key now lives on a different server. Every lookup misses, the whole cache rebuilds at once, and all that load slams the database — this is a cache stampede. One tiny change (adding a server) invalidated the entire cache.

The story: a round clock face and clockwise helpers

Imagine a round clock face. Standing around its edge are a few helpers — one at 2 o'clock, one at 5, one at 9. Slips of work (items) are also placed around the clock at various spots. The rule is simple: each slip belongs to the helper standing next clockwise from it.

Now one helper (the one at 5) goes home. What happens? Only the slips that used to fall in their slice now go to the next clockwise helper (the one at 9). Every other slip stays exactly where it was — the 2 o'clock and 9 o'clock helpers keep doing the same work as before. Adding a new helper is the same: they stand at one spot on the clock and take over just the slice in front of them, without redistributing all the work.

Map it to tech: clock face = the hash ring. Helpers = servers (each placed at a spot on the ring). Slips = keys (also hashed onto the ring). "Next clockwise helper" = the server that owns the key. A helper joining or leaving only shifts the keys near it, not all of them.

Quick check: with hash(key) % N, how many keys move when you go 4 → 5 servers? And with the ring?
With % N: nearly all keys (N changed, so every answer changed). With the ring: only ~1/N of keys — the ones that fall right next to the new server. That's the whole point of consistent hashing.

A small snag: uneven load, and its fix (virtual nodes)

If each server sits at just one spot on the ring, unlucky placement can put those points close together, giving one server far more keys than the rest. The fix: place each server at several points (virtual nodes) on the ring — say 100 small points per real server. Now keys spread out much more evenly, because each server's "slice" is scattered all around the ring.

Django bridge Remember sharding (12)? There you decided which row goes to which shard. Consistent hashing is that same decision but with smooth scaling. The most direct place you touch this in Django: the distributed cache. When you run a cluster of Memcached or Redis (not a single node), the client must decide which key lives on which node — and it often uses consistent hashing. That's why you can add or remove a cache node without invalidating the whole cache. Inside Django you just point CACHES at a cluster; the ring works underneath so your cache.get()/cache.set() survive a deploy.
The tradeoff: name it in interviews Consistent hashing is more complex than hash(key) % N — you must maintain a ring and a sorted structure for clockwise lookups. And without virtual nodes the load can be uneven, turning one node into a hot spot. So it isn't free: you trade a little simplicity to avoid the massive reshuffle on add/remove. For a small, fixed cluster plain modulo is fine; where you scale up/down often, consistent hashing wins.

Your win today hash(key) % N reshuffles everything on add/remove (cache stampede). Consistent hashing places servers and keys on a ring — each key belongs to the next server clockwise — so adding/removing a node moves only ~1/N of keys. Virtual nodes keep the load even. This is what lets distributed caches, sharded databases, and load distribution scale smoothly — and saying "ring + virtual nodes" in an interview is a strong signal.
