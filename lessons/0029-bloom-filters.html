Bloom filters: "definitely not" or "probably yes"

A tiny, super-fast data structure you ask before an expensive lookup — and if it says "not there," you skip the whole check.

~7 min One concept: Bloom filter Win: skip expensive lookups safely

30-second warm-up (recall caching)

From memory: why do we keep a cache? One line.
So we don't hit the expensive thing (disk, database, network) again and again — if the answer's already near, serve it fast. A Bloom filter is the same spirit: avoid an expensive lookup — except it saves you by saying "no," not by holding the answer.
click to reveal — say it first
If you remember one thing A Bloom filter tells you one of two things: "this item is DEFINITELY not in the set" (100% sure) or "this item is PROBABLY in the set" (small chance of being wrong). No false negatives — only occasional false positives. That's why you can trust "definitely not" and skip the expensive check.

The story: a bouncer with a rough guest list

Picture a club bouncer at the gate. Inside there's a thick, detailed guest list (the full database) that takes time to check. In the bouncer's hand is just a rough note — a few markers that let him guess instantly.

  • You arrive. The bouncer glances at his rough note and says: "Your markers aren't here at all — you're definitely not on the list. Turn back." He never opens the thick list. Instant, and 100% correct.
  • Or he says: "Your markers match — you're probably on the list. Come in, now let me confirm your name in the thick list." Here he does the full check — because maybe someone else's markers matched by coincidence (that's a false positive).

Notice: the bouncer never wrongly told a real guest "no." If you're on the list, your markers will match. "Definitely not" is always true — only "probably yes" is sometimes wrong. That's a Bloom filter.

How it works (lightly)

  • Keep a small bit array (just 0s and 1s), all zero to start.
  • To add an item: run it through a few hash functions that point to a few positions in the array — set those positions to 1.
  • To ask "is X here?": run the same hashes. If any position is 0 → X is definitely not (adding it would have set that bit). If all are 1 → X is probably here (those bits may have been set by other items).

That's why false negatives are impossible and false positives are possible: an added item always leaves all its bits at 1, but overlapping bits can occasionally make a never-added item look "probably here."

Django bridge Say you keep asking "has this user seen this article?" or "does this username already exist?" — each one is an expensive DB query. Keep a Bloom filter in memory: if it says "definitely not," you move on instantly without running User.objects.filter(...); only on "probably" do you hit the DB. Redis has Bloom filter support (the RedisBloom module — BF.ADD / BF.EXISTS), so you can share one across your workers. And this isn't just theory — Cassandra and HBase use Bloom filters internally to skip a disk read for a key when it's definitely not in that file.
Quick check: the Bloom filter says "probably yes." Can you trust it and serve the item directly?
No. "Probably yes" can be wrong (a false positive), so you now do the real expensive lookup to confirm. You only fully trust the other side: "definitely not" is always true, which is what lets you safely skip the full check.

The tradeoff — name it in interviews A Bloom filter isn't free. (1) You accept a small false-positive rate — it grows as you add more items or shrink the array (it's a tuning problem). (2) A plain Bloom filter can't easily remove items — clearing one bit could break other items (you'd need a variant like a Counting Bloom filter). In exchange you save huge time and memory. Interview line: "I'd put a Bloom filter in front to skip expensive lookups — no false negatives, just a tunable false-positive rate, and it can't handle removes."
