async / await: doing many waits at once

The other way to handle I/O — one worker who never sits idle. Builds straight on the GIL lesson.

~10 min One concept: async concurrency Win: know when async beats threads

30-second warm-up (recall the GIL)

From memory: the GIL means threads don't help which kind of work, but do help which other kind — and why?
Threads don't help CPU-bound work (only one holds the GIL/talking stick at a time) but do help I/O-bound work (a waiting thread drops the stick so others run). async is another way to win at that I/O-bound case.

If you remember one thing async lets a single worker start many slow I/O tasks and switch between them whenever one is "waiting," instead of sitting idle. One cook juggling many pots — not many cooks.

The story: one cook, many pots

A cook has to boil pasta (10 min), roast veg (15 min), and simmer sauce (8 min). A naive cook does them one at a time — 33 minutes. A smart cook starts the pasta, and while it boils, starts the veg, and while both cook, starts the sauce. Total time ≈ the longest single task, ~15 min. Same one cook — they just never stand around waiting.

That's async. The "waiting" (water boiling) is the I/O — network calls, database, disk. await is the cook saying "this is going to wait a while — let me go start something else meanwhile."

import asyncio

async def fetch(url):
    ...                        # await a slow network call
    return await http_get(url)

# start all three; they overlap their waiting
results = await asyncio.gather(fetch(a), fetch(b), fetch(c))

async vs threads — both help I/O, so which?

From the GIL lesson you know threads also help I/O-bound work. So what's the difference?

Threadsasync (asyncio)
Who switchesThe OS, anytime (pre-emptive)Your code, at each await (cooperative)
Cost eachHeavier (real OS threads)Very light (thousands cheaply)
Best atModerate I/O, mixing with blocking libsHuge numbers of I/O waits (thousands of connections)

Rule of thumb: a few dozen I/O tasks → threads are fine. Thousands of simultaneous connections (a chat server, a web scraper hitting 10,000 URLs) → async shines, because each one is cheap.

Django bridge Modern Django supports async def views and an async ORM path. It helps most when a view does lots of waiting — calling several external APIs, handling many long-lived connections (websockets via Channels). But careful: mixing await with old blocking code (a sync DB driver, time.sleep) stalls the whole event loop — one cook who insists on standing and watching one pot blocks all the others. And remember: async does not help CPU-bound work — that's still processes/Celery (from the GIL lesson).
Quick check: does async help CPU-bound work? And what's the one-line difference from threads?
No — async only helps I/O-bound (waiting) work, not CPU crunching (still needs processes). Difference from threads: async switches cooperatively at each await (your code decides) and is far lighter, so it scales to thousands of waits.

The classic async trap — name it One blocking call in async code (a sync library, time.sleep(5), heavy math) freezes the entire event loop — every other task stalls, because there's only one cook and they're stuck at one pot. The whole model depends on every task politely await-ing during waits. This "don't block the event loop" rule is the #1 thing that bites people.
