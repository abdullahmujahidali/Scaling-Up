API gateway: one front door for all your services

A single entry point that handles auth, rate limiting, and routing in one place — so each service doesn't repeat them.

~8 min One concept: API gateway Win: centralize cross-cutting concerns

From memory: what does a load balancer do, in one line?
A load balancer spreads incoming traffic across several identical server copies, so no single server gets overloaded. It's a front door that distributes. Today we meet a smarter front door — one that doesn't just spread, it thinks.

If you remember one thing An API gateway is a single entry point in front of your many backend services. It does every cross-cutting job — authentication, rate limiting, routing, logging — in ONE place, so each service doesn't rewrite them.

What "cross-cutting concern" means

  • Authentication: who is this request from? Every service needs to check this — or the gateway checks it once.
  • Rate limiting: stop a client from sending too many requests. Either each service enforces it, or the gateway does it once for all.
  • Routing: send /orders to the orders-service, /users to the users-service — look at the path, deliver to the right place.
  • Logging: record every request in one place, so you get one complete picture.

These are all cross-cutting — meaning every service needs them. If each service does it itself, you write the same code 10 times. The gateway does it once.

The story: the hotel front desk

Picture a big hotel with a hundred rooms. Every visitor who comes in — a guest, a delivery person, a technician — stops at one single front desk to check in. The receptionist checks your ID (that's authentication), decides whether to let you in, and then directs you to the right room (that's routing). They also keep a register of who came and when (that's logging).

Now flip it: if every room had its own guard, its own ID check, its own register — that security work would repeat a hundred times. Expensive, error-prone, and messy. That's why a hotel has one reception. An API gateway is just like that: each room (service) doesn't keep its own security — everyone passes through one front desk.

Django bridge Suppose you split a big Django monolith into several small services — a users-service, an orders-service, a payments-service. Each runs on DRF. Now the question: where do you put JWT auth and throttling? If you write it separately in each service, you maintain the same middleware in three places — and risk bugs in three places. Instead, put one API gateway (Kong, AWS API Gateway, or just nginx) in front of them all. It verifies the JWT once, applies throttling in one place, and then only forwards verified requests inward. Your Django services get thinner — they just think about their business logic, and security lives at the gateway.

Gateway vs load balancer

Both are front doors, but a load balancer is "dumb": it just splits traffic across identical copies. A gateway is "smart": it understands the request — it authenticates, it routes by path (/orders vs /users), and it can even transform the request when needed. Often there are load balancers behind the gateway too — they work together.

Quick check: how is a gateway "smarter" than a load balancer — name one difference.
A load balancer just spreads traffic (which server is free). A gateway looks at the request's content — it checks auth, picks the right service by path (routing), and can transform the request. Load balancer answers "which server", gateway answers "which service + what gets let in".

The tradeoff — name it in interviews A gateway is one more thing to run — an extra hop (every request goes through one more step, a little latency) and a single point of failure: if the gateway goes down, all services become unreachable even though they're perfectly fine inside. So make the gateway itself redundant — run several copies with a load balancer in front, so one gateway dying doesn't take the whole system down.

Your win today API gateway = one front desk in front of all your services. It handles cross-cutting concerns — auth, rate limiting, routing, logging — in one place, so each service doesn't repeat them. It's a front door like a load balancer but smarter (auth, path routing, transform). Tradeoff: an extra hop and a single point of failure — so make the gateway itself redundant. Saying "centralize cross-cutting concerns, but make the gateway HA" in an interview is a strong signal.
