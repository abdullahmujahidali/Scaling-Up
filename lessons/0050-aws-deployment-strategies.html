Deployment strategies: blue/green, canary, linear

Domain 3 is 24% of the exam and this is its most-asked topic. There are four approaches, and each has a phrase that appears in the question. Recognise the phrase and you have the answer.

If you remember one thing Every strategy answers one question: if the new version is bad, how many users get hurt, and how fast can you go back?

Blue/Green = zero downtime, instant rollback (but double the cost).
Canary = a small group first, then everyone (two steps).
Linear = equal slices, gradually (e.g. 10% every 10 minutes).
All-at-once = cheapest, but there is downtime.

The story: a restaurant's new dish

Your restaurant has invented a new curry. You don't know whether people will like it. Four approaches:

  • All-at-once: stop the old curry entirely, serve only the new one. If it's bad, every customer today is unhappy. Cheapest, riskiest.
  • Canary: serve the new curry to 5 customers first. They're happy? Roll it out to everyone. Unhappy? Only 5 people were affected. (A "canary" was the bird taken into coal mines to detect gas first — a small loss that prevents a disaster.)
  • Linear: each hour, 10% more customers get the new curry. Gradually everyone. Spot a problem and you stop.
  • Blue/Green: build a second, complete kitchen next door cooking the new curry. When it's ready, send all customers to that room. Bad? Send them straight back to the old room — a 10-second job. But you paid rent on two kitchens.

"replace instances in batches, reduced capacity is acceptable" Rolling Capacity drops during the deployment.
Lambda deployment names — how CodeDeploy writes them
  • Canary10Percent5Minutes = 10% of traffic first, wait 5 minutes, then the remaining 100%. Two steps.
  • Linear10PercentEvery10Minutes = 10% more every 10 minutes. Ten steps.
  • AllAtOnce = all traffic to the new version immediately.
  • These names appear on the exam exactly like this — learn to read them; the name itself tells you the behaviour.
Trap — buildspec vs appspec Two files, and the exam swaps them to trick you:

buildspec.yml → belongs to CodeBuild. It describes how to build and test the code.
appspec.yml → belongs to CodeDeploy. It describes how to deploy the new version and which hooks to run.

Memory hook: buildspec = the service that builds. appspec = the service that puts the app in place.
Exam English — deployment words "downtime" = time when the service is unavailable. "roll back" = return to the previous version. "cut over" = switch traffic to the new version. "shift traffic" = the same thing. "in place" = upgrade on the same servers (no new ones). "immutable" = the old ones are never touched; new servers are built instead.

Bridge to your Django work You make this decision on every release. When you deploy a Django app by running migrate and restarting gunicorn — that's all-at-once, and it's exactly where those few seconds of downtime you've seen come from. When you bring up new servers with the new version and repoint the load balancer — that's blue/green. And when you enable a feature for just 5% of users (feature flags — lesson 0035) — that's precisely canary thinking. You have done all of this; the exam only asks for the names.
