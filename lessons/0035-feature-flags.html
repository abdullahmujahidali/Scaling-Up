Feature flags: turn features on and off without deploying

A switch inside your code — no deploy needed. Ship a feature hidden, open it to 5% of users, or kill a broken feature in one second.

~8 min One concept: feature flags Win: ship safely, kill instantly

30-second warm-up (recall deployment safety)

From memory: when a new deploy has a bug, how do you take it back — and how fast is that?
You do a rollback — redeploy the old version. But a rollback is slow: build, deploy, restart servers — it can take minutes, and users keep hitting the bug the whole time. We're about to see a way that's instant.

If you remember one thing A feature flag is a switch that turns a feature ON or OFF inside your code — driven by config or a database, without deploying new code. That means you can ship a feature hidden, roll it out gradually, and instantly turn off a broken one — with no rollback deploy.

Three things flags give you

  • Dark launch: the code is deployed but OFF — it's in production, invisible to users. Deploy and "release" become separate events.
  • Gradual rollout: open the feature to 5% of users, then 25%, then 100% — problems are caught before they spread.
  • Kill switch: if the new feature breaks, flip the flag OFF — in one second, no rollback. Incident over.

A/B testing comes from the same idea: give 50% of users the new checkout, 50% the old one, and compare which converts better.

The story: a dimmer switch and a valve at home

Imagine you install a new, powerful light at home. If it were hardwired straight into the wall, then to turn it on or off you'd have to open the wall and rewire it — messy, slow, and risky. Now imagine you wire it to a dimmer switch instead.

  • Turn it on slowly: nudge the dimmer — the light comes on at 5%. Eyes adjust, no shock. (= rollout to 5% of users.)
  • Shut it instantly: if the bulb sparks, flip the dimmer off — instantly. You don't break open the wall. (= kill switch.)

Rewiring the wall = deploying new code (slow, risky). Turning the dimmer = flipping a flag (instant, safe). That's a feature flag: a switch that gives you control without rewiring the house (redeploying).

Django bridge The simplest flag is a boolean in settings.py or the database: NEW_CHECKOUT_ENABLED = False. In a view you check if settings.NEW_CHECKOUT_ENABLED:. When you need per-user rollout, use a library like django-waffle and write if flag_is_active(request, 'new_checkout'): — waffle can turn a flag on for a user, a group, or a percentage of users (the 5% rollout becomes an admin setting, not a code change). During an incident you just flip the value OFF in the admin/DB — a kill switch, no redeploy. This ties straight to deployment safety: you separate "deploy" from "release."
Quick check: how is flipping a flag to disable a broken feature better than a rollback deploy?
A flag flip is instant — you change one config/DB value, no build or deploy, no restart. A rollback means redeploying the old version, which can take minutes, and users keep hitting the bug meanwhile. With a flag, the incident ends in seconds.

The tradeoff — name it in interviews Flags become tech debt. Every flag adds an if branch in the code. After rollout, if you don't clean up old flags, those stale flags clutter the code, and too many flags make the system's behavior hard to reason about (2^N combinations). Rule: clean up the flag after rollout — make the winning path permanent in code and delete the flag.

Your win today Feature flag: a config/DB-driven switch that turns a feature ON/OFF with no deploy. With it you can dark launch, gradually roll out (5% of users), A/B test, and instantly kill a broken feature. In Django: a boolean setting, or flag_is_active(request, 'new_checkout') with django-waffle. Just remember — stale flags are tech debt, clean them up after rollout.
