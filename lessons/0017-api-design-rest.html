API design: how systems talk (REST)

If you remember one thing REST models your API as "nouns" (resources, at URLs) that you act on with a small set of HTTP "verbs" (GET, POST, PUT, PATCH, DELETE). Nouns in the URL, verbs as the action.

The story: a library counter

Think of your API as a library counter. The things are books, members, loans — those are resources (nouns), each with an address (a URL). The actions are few and standard: look at, add, replace, tweak, remove. REST's whole trick is: keep the nouns in the URL and use the same tiny set of verbs for the actions.

The verbs (HTTP methods)

VerbMeansExample
GETread (never changes anything)GET /books · GET /books/42
POSTcreate a new onePOST /books
PUTreplace an existing one fullyPUT /books/42
PATCHupdate part of onePATCH /books/42
DELETEremove oneDELETE /books/42

Notice the pattern: the URL /books/42 stays the same — the verb changes what you do to it. That's the elegance. You don't invent /deleteBook and /updateBook endpoints; you use DELETE and PATCH on the same resource URL.

The status codes (self-describing answers)

The response tells you what happened with a status code — no guessing:

  • 2xx = success (200 OK, 201 Created)
  • 4xx = you (the client) messed up (400 bad request, 401 unauthorized, 404 not found, 429 too many requests)
  • 5xx = the server messed up (500 internal error, 503 busy — remember back pressure!)
Django bridge Django REST Framework is this lesson made concrete. A ViewSet maps those verbs to methods automatically: GET /books/ → list(), POST /books/ → create(), GET /books/42/ → retrieve(), DELETE /books/42/ → destroy(). A router builds the clean URLs for you. When you design a DRF API, you're doing REST design — this lesson is the "why" under the framework you already touch.
Quick check: to update part of an existing user (id 7), what verb and URL? And what does a 404 tell the client?
PATCH /users/7 (partial update on that resource). A 404 means the resource wasn't found — and 4xx means the client's side of the request was the problem.

A lighter touch: REST vs RPC

You'll hear "REST vs RPC." Keep it simple: REST exposes data (nouns) using standard verbs — great for public APIs everyone can understand. RPC exposes actions (you call a named function like chargeCard() on a remote server) — great for fast internal service-to-service calls. Most web APIs you build are REST; internal microservice chatter often uses RPC (e.g. gRPC).

REST's real limits — name them REST isn't perfect: fetching nested data ("give me this user and their orders and each order's items") can take multiple round-trips, and clients get every field whether they need it or not. That's exactly why GraphQL exists (fetch precisely what you ask for). Knowing REST's weak spots — not just praising it — is the senior signal.

Your win today REST = nouns in the URL (resources), a small fixed set of verbs (GET/POST/PUT/PATCH/DELETE) for actions, and status codes that self-describe (2xx ok, 4xx client's fault, 5xx server's fault). Same URL, different verb. This is the "why" beneath Django REST Framework — and clean API design is a daily-job and interview staple.
