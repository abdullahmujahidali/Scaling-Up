Event streaming (Kafka) vs message queues: one job vs one log

A queue does a job once, then it's gone. A stream is a permanent log many readers can each read at their own pace.

~8 min One concept: log vs queue Win: know when to reach for Kafka

30-second warm-up (recall message queues)

From memory: how does a message queue (like Celery + RabbitMQ) work?
Your web request drops a task into a queue and returns immediately. A background worker picks the task up, runs it (send an email, resize an image), and the task is removed from the queue. One job → one worker → done. Today we see when that "take it once then delete" model isn't enough.
click to reveal — say it first
If you remember one thing In a queue, each message is taken by one worker and then it's gone. An event stream (Kafka) is an append-only log: an event is written and stays there, and many separate consumers can each read it independently, at their own pace — and re-read it.

The story: ticket counter vs newspaper archive

Picture a single-line ticket counter. Each customer takes a ticket, one clerk serves it, then that ticket is done — no one ever sees it again. Exactly one clerk handles each ticket. That's a message queue: one job, one worker, then removed.

Now picture a newspaper archive — or the full history of a WhatsApp group chat. A story is published (an event) and stays there permanently. Many different people can read it: one reader today, one again tomorrow, a researcher six months later. Each reads from wherever they want, at their own pace, and the story is never deleted. That's an event stream.

The difference: a queue is for "hand out work and delete it." A stream is for "this happened, let whoever cares react" — and the record stays.

Kafka's four simple words

  • Topic — a named log, like a channel. Example: an orders topic where every "order placed" event goes.
  • Producer — whoever writes events. Your Django app produces an event when an order is created.
  • Consumer — whoever reads events. The email service, inventory service, and analytics are separate consumers — all reading the same events.
  • Partition — a topic is split into pieces so events can be processed in parallel. More partitions = more consumers working at once (throughput). That's all you need to grasp.
Django bridge Your everyday work is handled by Celery + RabbitMQ/Redis: a user signs up → drop a welcome-email task on the queue → a worker sends it. One job, one worker, done. Don't reach for Kafka here. Reach for Kafka when: (1) many systems must react to the same event — "order placed" needs to trigger the email service and inventory service and analytics, and you don't want to touch the producer for every new consumer; (2) you need replay — a new analytics feature ships, reprocess old events; or a consumer crashes, resume from where it left off; (3) very high throughput (millions of events per second) a simple queue can't handle. A quick rule: if you're thinking "work's done, delete it," Celery is enough; if you're thinking "this happened, tell several systems and keep the record," reach for Kafka.
Quick check: the single biggest difference between a queue and a Kafka topic, in one line?
Queue: a message is taken by one consumer and then deleted. Kafka topic: the event stays in a log, so many consumers can each read it and re-read it (replay).

The tradeoff — name it in interviews Kafka is very powerful, but it's heavier to run and operate than a simple queue: brokers, partitions, replication, consumer offsets — a whole cluster to monitor. For a small app that just needs background tasks, Kafka is over-engineering — Celery + RabbitMQ does the same job with far less operational load. The right move: the simplest tool that works. Justify Kafka by need (many consumers, replay, high throughput), not by hype.
An "order placed" event must trigger the email service, inventory service, and analytics — all three — and you want new consumers to be able to re-read past orders later. Better fit?
Your Django app needs to send a welcome email after signup — just one worker sends it, nobody re-reads it, low volume. Most appropriate?
Your win today A queue = one job taken by one worker, then removed (a to-do list). An event stream / Kafka = an append-only log that many consumers each read at their own pace, and events stay (can be replayed). Kafka's four words: topic, producer, consumer, partition. Reach for Kafka when many systems react to the same event, you need replay, or throughput is very high — otherwise Celery is enough. Cleanly stating "a queue deletes, a log keeps" in an interview is a strong signal.
