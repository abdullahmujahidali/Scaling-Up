Trees & BST: cut the work in half at every step

A root that branches into children — and a sorted version (BST) that makes search O(log n), the same "keep halving" idea as binary search.

~8 min One concept: tree & BST Win: know why an index is O(log n)

30-second warm-up (recall binary search)

From memory: what does binary search do on each guess in a sorted list, and why is it O(log n)?
It looks at the middle, compares to the target, and throws away the other half — then again, then again. Because each step halves the search space, 1000 items take only ~10 guesses. Today we'll see how a tree stores that same "keep halving" idea as a structure.

If you remember one thing A tree branches from a root; a Binary Search Tree keeps it sorted — smaller values go left, bigger go right — so each step halves the search (O(log n)). It's like "20 questions": every answer cuts the possibilities in half.

First: what a tree is

  • Root: the top node — where everything starts (like the oldest ancestor in a family tree).
  • Children: each node branches down into other nodes. Each node has exactly one parent.
  • No cycles: you never loop back to the same node — it always flows downward (like a family tree or an org chart).

An org chart, file-system folders, the HTML DOM — all trees. A Binary Search Tree (BST) is a special tree with two rules: each node has at most two children (left and right), and values are kept sorted.

The story: guessing age in a sorted family tree

Imagine a family tree where under each person sit two people: left is the younger one, right is the older one. You're hunting for someone's age — say 34. You stand at the root: "Are you 50?" They say "I'm 50." 34 < 50, so you go left (the younger side) — the whole right branch is gone in one move. Next person is 20: 34 > 20, so go right. In just two questions you've dropped half the people each time.

This is the "20 questions" guessing game. Each node is a yes/no branch. Because the tree is sorted, every answer cuts the search space in half — so even among 1000 people you arrive in ~10 questions. This is binary search, just shaped as a tree.

Django/Python bridge Remember adding db_index=True to a column and the lookup got fast? Postgres stores that index as a B-tree — a balanced tree tuned for disk (each node holds many children to cut disk reads). When you run User.objects.get(email=...), Postgres does not scan every row (O(n)) — it walks down the B-tree from the root, halving (or more) the range at each step, so the lookup is O(log n). That is why an indexed lookup is fast — the "under the hood" of the database-index lesson (B2). And outside the DB too: your project's folders are a tree, an org chart is a tree, a DRF nested serializer output is a tree.
Quick check: in a BST you're searching for 90 and the root is 50. Do you go left or right, and why?
Right. 90 > 50, and the BST rule says bigger values go right — so the whole left branch (everything smaller than 50) is eliminated in one step. Each compare cuts the search space in half, which is why it's O(log n).

The tradeoff — name it in interviews A tree stays fast only while it's balanced. If you insert already-sorted data into a plain BST (10, 20, 34, 50, 70…), every node gets only a right child — the tree becomes a straight line, exactly like a linked list. Now search is O(n) again, not log n — the halving is gone. That's why real databases use self-balancing trees (Postgres's B-tree, or red-black/AVL trees) that re-arrange themselves on insert to stay short (balanced). Interview line: "a BST is O(log n) only if it stays balanced; unbalanced it degrades to O(n), so real systems use self-balancing trees."

Your win today You now understand trees: a root that branches into children, no cycles, one parent per node. A BST keeps values sorted (smaller left, bigger right) so search halves at every step — O(log n), just like binary search. That's the reason a Postgres index (a B-tree) is O(log n) not O(n). And you know the tradeoff: the tree must stay balanced or it degrades into a linked list at O(n) — which is why real databases use self-balancing trees.
