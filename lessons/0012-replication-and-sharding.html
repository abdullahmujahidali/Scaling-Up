Replication & Sharding: how databases actually scale

Two moves: copy the data (for reads) and split the data (for size). Different problems, different fixes.

~9 min Two related tools: replication & sharding Win: know which one solves which problem

If you remember one thing Replication = keep full COPIES of the database (helps you serve more reads). Sharding = SPLIT the data across machines (helps when the data is too big for one). Copy vs split — different problems.

Replication — copy the whole thing

Story: a popular library book everyone wants to read. Instead of one copy with a huge queue, you make several identical copies. Everyone can read at once. You already met this: a read replica from the consistency lesson.

  • Master–slave (primary–replica): one machine takes writes (the master), copies them to read-only replicas. Reads spread across replicas; writes all go to the master. Great for read-heavy apps.
  • Master–master: two machines both take writes and sync to each other. More availability, but now you can get conflicts (both edited the same thing) that need resolving.

What replication solves: too many reads for one machine. What it does NOT solve: the data being too big — every copy is still the whole thing.

Sharding — split the data up

Story: one phone book for the whole country is too fat to lift. So you split it: A–H in one book, I–P in another, Q–Z in a third. Each is smaller and faster to search. That's sharding — each machine (shard) holds a slice of the data, chosen by some key (e.g. user ID, region).

  • Less data per machine → faster, more fits in memory.
  • Writes spread out → you can handle way more of them.

What sharding solves: data (or write load) too big for one machine. The cost: your app must know which shard holds what, and queries that cross shards (joins, "count all users") get painful.

Django bridge Replication is easy to adopt in Django: configure a replica in DATABASES and a database router to send reads to the replica, writes to the primary — reads scale, and you accept eventual consistency (2a) on the replica. Sharding is much heavier: Django has no built-in sharding, so it means app-level routing or a tool like Citus. The lesson: replicate first (cheap, common); shard only when data size truly forces it (expensive, rare).
Quick check: your app has too many reads for one database — replicate or shard? What if the data is simply too big for one machine?
Too many reads → replication (more copies to read from). Data too big → sharding (split it across machines). Copy for reads, split for size.

Order of operations (interview gold) When scaling a database, the usual ladder is: 1) index & tune queries → 2) add caching → 3) add read replicas → 4) shard (last resort). Sharding is powerful but adds the most complexity, so it's the final move, not the first. Reaching for sharding too early is a classic junior mistake — knowing the ladder is the senior signal.
Your app is read-heavy: tons of users viewing pages, few writes. One database is maxed on reads. Cheapest effective fix?
Your single database can't physically hold or write the sheer volume of data anymore, even with replicas. What's the tool for that?
Your win today Replication = copies (fixes too many reads; you met it as read replicas). Sharding = split (fixes data too big). The scaling ladder: index → cache → replicate → shard, with sharding last because it's the most complex. Knowing which tool fits which problem is exactly the judgment interviews and real architecture reward.
