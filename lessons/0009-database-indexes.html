Indexes: why one query is instant and another crawls

The single highest-leverage database skill for daily Django work.

If you remember one thing An index is like the index at the back of a book — it lets the database jump straight to the rows you want instead of reading every row. Without it, the DB reads the whole table.

The story: finding a word in a book

You want every page that mentions "Django" in a 900-page book. Two ways:

  • No index: read the book cover to cover, page by page, noting each mention. Slow. This is a full table scan.
  • With an index: flip to the alphabetical index at the back, find "Django → pages 12, 88, 340." Instant. This is an index lookup.

A database index is exactly that back-of-book index, but for a column. Search that column a lot? Add an index and the DB stops reading the whole table.

Reading the truth: EXPLAIN

How do you know if a query uses an index or scans everything? You ask the database with EXPLAIN. It shows the plan. The words to watch for:

  • Seq Scan (sequential scan) — reading the whole table. Fine for tiny tables; a red flag on big ones.
  • Index Scan — using an index to jump. What you usually want for lookups.
Django bridge — you've already made indexes without noticing Every Django model's primary key is indexed automatically. A ForeignKey is indexed too. But filter often on a plain field — User.objects.filter(email=...) — and that column is not indexed unless you say so: db_index=True on the field, or Meta.indexes. To see the plan, run print(qs.explain()) on a queryset. If you see "Seq Scan" on a big table you filter constantly, that's your slow query — and adding an index is usually the fix.
Quick check: in an EXPLAIN output, which is usually the warning sign on a large table — "Seq Scan" or "Index Scan"?
Seq Scan — the database is reading the whole table row by row. On a large, frequently-filtered table, that's the cue to add an index (which turns it into an Index Scan).

Indexes aren't free (the tradeoff — name it) An index makes reads faster but writes slower — every insert/update must also update the index (like re-sorting the back-of-book index every time you add a page). Indexes also take disk space. So you don't index everything — you index the columns you search or sort by often. Read-heavy column → index. Rarely-queried column → skip it. That read-vs-write tradeoff should sound familiar by now.
Your Django app filters Order.objects.filter(customer_email=...) constantly, the table has 5M rows, and it's slow. explain() shows "Seq Scan." Best first move?
Why not just index every column to be safe?
Your win today An index = the back-of-book index: the DB jumps to rows instead of reading them all. EXPLAIN tells you which is happening ("Seq Scan" = reading everything, a red flag on big tables). Indexes speed reads but slow writes — so index the columns you filter/sort by often. This one skill fixes a huge share of real slow-query problems.
