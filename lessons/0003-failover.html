Failover: staying up when a server dies

If you remember one thing Failover = keeping a spare server ready, so when one machine dies, another takes over and users barely notice. The two flavors differ on whether the spare is sitting idle or already working too.

Start with a story (no tech yet)

You run a small shop with one cashier at the till. If that cashier faints, the line stops — nobody can pay. Bad. So you hire a second person. Now you have a choice about what the second person does:

  • Plan A: the second person sits in the break room, ready. If the cashier faints, they rush out and take over the same till. (Only one works at a time.)
  • Plan B: you open a second till and both serve customers at once. If one faints, the other just keeps going — the line's a bit slower, but it never stops.

That's the entire idea. Plan A is active–passive. Plan B is active–active. Let's name the moving parts.

1 · Active–passive — "a spare waiting in the break room"

One server does all the work. The spare sits idle but listening. The two send each other a heartbeat — a little "still alive?" ping every second or so. The instant the spare stops hearing it, it assumes the worker died and takes over its address, so traffic now flows to the spare.

How fast does that switchover happen? Depends on the spare:

  • Hot spare — already booted and warm → takes over in seconds.
  • Cold spare — has to start up first → slower, but cheaper to keep around.
Quick check: in active–passive, what is the heartbeat for?
It's the "still alive?" signal between the two servers. When the spare stops hearing the heartbeat, it knows the active one died and takes over.

2 · Active–active — "two open tills"

Both servers serve real traffic at the same time and split the load between them. If one dies, the other simply takes on all the work. The trade: everyone has to know both exist. If it's public-facing, the address system (DNS) must list both; if it's internal, your app code has to know about both.

Quick check: what's the main difference between active–passive and active–active?
In active–passive, the spare sits idle until needed (only one works at a time). In active–active, both work at once and share the load.

The catch nobody mentions

Failover isn't free Two real costs: (1) more complexity — extra machines, extra setup, more that can go wrong. (2) possible data loss — if the active server dies before it copied its newest changes to the spare, those changes are gone. (Notice that's the same idea as the catch-up gap from consistency in 2a — the copy was behind.)
Django / real-work bridge A managed database like AWS RDS offers "Multi-AZ" — that's active–passive failover: a standby copy in another data center, and if your main database dies, RDS flips to the standby automatically. You've probably ticked that checkbox without knowing its name. Now you know what it's doing and what it costs.

Pull it together + one quiz

Cover the answer. Explain both failover types using the shop story.
Active–passive — a second cashier waits in the break room; rushes out (takes over) only when the first faints. One works at a time.
Active–active — two tills open at once, splitting the line; if one cashier faints the other carries everyone.

You want a backup database that's as cheap as possible, and you're OK with a short pause (a few seconds) while it switches over during a failure. Which fits best?
Your win today Failover is just "keep a spare so you don't go down." Active–passive = a spare waiting in the break room (cheaper, slower switch). Active–active = two open tills (pricier, no pause). And it's not free — more complexity, and you can lose the newest data if the spare was behind. One clean idea, yours.
