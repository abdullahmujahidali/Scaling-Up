WebSockets: a connection that stays open

In normal HTTP the server can't push to you on its own. WebSocket tears down that one wall.

~8 min One concept: WebSockets Win: know when to keep a connection open

30-second warm-up (recall the HTTP request/response cycle)

From memory: what is the full lifecycle of one normal HTTP request?
Client sends a request → server sends a response → the connection closes. Done. The server can't "ring you back"; the client has to ask again to get new data. Hold on to the fact that the server can never speak first — that's exactly what we're about to fix.
click to reveal — say it first
If you remember one thing HTTP is like mailing letters — the client asks, the server answers, then the connection closes. A WebSocket is like a phone call that stays on — either side can speak whenever it wants, as often as it wants, instantly. That's the whole difference.

The story: mailing letters vs a walkie-talkie

Imagine you're talking to a friend. HTTP is like mailing letters. You write a letter ("any news?"), post it, and wait. They reply. Conversation over. If you want to know whether anything else happened, you have to write a new letter. Your friend can't send you a letter out of the blue when you didn't ask — they don't even know where you are or whether you're listening.

Now, a WebSocket is a walkie-talkie (or an open phone line). Once you "open the channel," the line stays open. You can talk whenever you like, and — this is the key part — your friend can also talk whenever they like, without waiting for you to ask. "Score just changed!" "New message arrived!" They can push it on their own. We call this a persistent, two-way connection.

Map it: a letter = one HTTP request/response that closes. The walkie-talkie = a WebSocket that stays open so the server can push to the client too.

When to use it — and when not to

  • Use it when the server needs to push to the client on its own: chat/messaging, live notifications, live scores, collaborative editing (Google Docs style), trading tickers, "user is typing…" indicators.
  • Don't use it for normal pages — a blog post, a profile screen, a product listing, a form submit. These are request/response: the client asks, gets one answer, done. A WebSocket here just wastes resources.

Simple rule: if new data arrives from the server side without the client asking, think WebSocket. If the client always asks first, plain HTTP is fine.

Quick check: a team asks the server every 2 seconds for "live scores" (polling). What does a WebSocket fix?
Polling is wasteful: it fires thousands of requests even when nothing changed, and updates still arrive up to 2 seconds late. With a WebSocket the server pushes only the moment the score actually changes — fewer requests, instant, and the server speaks on its own. Exactly the walkie-talkie win.

Django bridge Your normal Django runs on a WSGI server (gunicorn/uWSGI) — it takes a request, returns a response, done. WSGI has no concept of a persistent connection at all. For WebSockets you need ASGI (an async server like uvicorn or daphne) plus Django Channels. Channels adds a consumer — it's like a view, but for a WebSocket connection: it has connect, receive, and disconnect methods instead of handling one request. Your normal HTTP views keep working exactly as before; Channels just layers on top for the real-time routes. So "WSGI vs ASGI" is really the infrastructure version of "letters vs open line."
Quick check: what's the core difference between a normal Django view and a Channels consumer?
A view handles one request and finishes by returning a response. A consumer lives for the entire lifetime of a connection — it opens on connect, takes as many messages as you want via receive, and can push from the server side whenever, until disconnect.

The tradeoff — name it in interviews Every open WebSocket holds memory and an open connection on the server — even when nothing is being sent. Normal HTTP is stateless: handle the request, free the memory, move on — that's why it scales cheaply. Persistent connections are stateful: 100,000 open sockets = 100,000 things the server keeps alive in RAM. That's harder to scale — you need more memory, care about connection limits, and a shared layer (like Redis) for multi-server so a socket open on one server can receive a message from another. One line for an interview: "WebSockets are stateful, so they're more expensive to scale than HTTP's stateless request/response."

In an interview: why are persistent WebSocket connections harder to scale than normal stateless HTTP?
Your win today HTTP = letters (client asks, server answers, connection closes — the server can't speak first). WebSocket = a walkie-talkie / open phone line: a persistent, two-way connection so the server can push on its own. Use it for chat, live notifications, live scores; not for normal pages. In Django that means ASGI + Channels consumers, not WSGI views. And the tradeoff you can name: persistent connections are stateful, so they're costlier to scale than stateless HTTP.
