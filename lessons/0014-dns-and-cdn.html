DNS & CDN: how a request even finds you

The two things that happen before your server ever sees a request. Two ideas, two stories.

~9 min Two front-door concepts: DNS & CDN Win: explain how users reach your app fast

30-second warm-up (recall Week 1: queues)

From memory: what does a message queue let a web request do, and why is that good?
It lets the request drop a slow job in a line and return immediately, while a background worker does the heavy part later. The user isn't stuck waiting. (That's async work — think Celery.)

If you remember one thing DNS turns a name (example.com) into an address (an IP). A CDN keeps copies of your files close to users around the world so they load fast. Both happen before your app server does any work.

Part 1 · DNS — the internet's phone book

Story: you want to call "Ali's Pizza" but you only know the name, not the number. You look it up in a phone book, get the number, then dial. DNS is that phone book for the internet. You type example.com (a name); DNS looks up its IP address (the number); your browser then connects to that address.

A couple of things worth knowing:

  • It's cached. Your browser and OS remember the lookup for a while (a TTL — same "let it go stale after N seconds" idea from caching). So it's not looked up every single time.
  • Record types — the phone book has different entry kinds. The main one: an A record maps a name → an IP. A CNAME maps a name → another name (an alias). You don't need the rest yet.
  • Managed DNS (Cloudflare, Route 53) can route smartly — send users to the nearest or least-loaded server (geolocation / latency-based routing).
The catch DNS adds a small delay (the lookup), and it's a juicy target — a big DDoS attack on DNS can take whole websites offline even if the sites themselves are fine, because nobody can find their address. That's why serious sites use resilient managed DNS.

Part 2 · CDN — copies of your files, near everyone

Story: your shop's warehouse is in Karachi. A customer in London orders a poster — shipping from Karachi is slow. So you keep copies of your popular posters in a London warehouse too, and one in New York, and Tokyo. Now everyone gets theirs from a nearby shelf. That's a CDN — a global network of servers holding copies of your static files (images, CSS, JS, video) close to users.

Two ways the copies get there:

TypeHow copies arriveBest for
Push CDNYou upload files to the CDN yourself, up frontSmaller sites, content that rarely changes
Pull CDNCDN fetches from your server the first time it's requested, then keeps itHigh-traffic sites (first request is slow, rest are fast)
Django bridge You've met this: in production you run collectstatic and serve your CSS/JS/images from a CDN (via S3 + CloudFront, or Whitenoise + a CDN in front) — not from Django itself. Why? Django's job is dynamic pages; static files are better served as cached copies near the user. Same "keep a copy closer" idea as the caching lesson, but spread across the globe. Your Django server never even sees those requests — the CDN answers them.
Quick check: one line each — what does DNS do, and what does a CDN do?
DNS turns a name (example.com) into an IP address so your browser can connect. CDN keeps copies of static files on servers near users worldwide so they load fast.

CDN's tradeoff — name it A CDN copy can be stale if you update a file before its TTL expires (that's why you'll see cache-busting like style.css?v=5 in filenames). And CDNs cost money at high traffic. Speed vs. staleness vs. cost — the same tradeoff family you keep meeting.
Users worldwide complain your site's images load slowly, though your server is healthy. Images are static. Best fix?
You type a domain and the browser needs the server's IP address to connect. What provides that translation?
Your win today Before your app runs: DNS (the phone book) turns the name into an IP, and a CDN (global warehouses) serves static files from near the user. Both are cached, both trade a little staleness for speed. Now the full path — DNS → CDN → load balancer → server → cache → database — makes sense end to end.
