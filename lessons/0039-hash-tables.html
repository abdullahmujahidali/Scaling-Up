Hash tables: why a dict is so fast

The data structure behind Python's dict and set — it gives near-instant O(1) lookup by key.

~8 min One concept: hashing Win: know why dict lookup beats list search

30-second warm-up (recall Big-O)

From memory: O(1) vs O(n) — one line each.
O(1) — constant time: no matter how big the data, the work stays the same (jump straight to one spot). O(n) — linear: double the data, double the work (check items one by one). Today we'll see how a dict lookup is O(1) while a list search is O(n).

If you remember one thing A hash table turns your key into a number (hashing), and that number points straight to the slot where the value lives — so lookup is near-instant O(1), without scanning the whole list. That's exactly what's inside a dict and a set.

The story: a coat-check with numbered hooks

Picture the coat-check counter at a fancy restaurant. The old way, your coat hangs in a line of 300 coats — to get it back, the attendant checks every coat one by one until they find yours. That's O(n): more coats, longer search.

Now the smart way. When you hand over your coat, you get a numbered ticket — say #57. The coat hangs on hook number 57. To collect it you show the ticket, and the attendant walks straight to hook 57. No searching. Whether there are 300 coats or 30,000 — it's one step. That's O(1).

Now map it: your coat = value, your name = key, and the thing that turns the name into a ticket number = the hash function. That ticket number = the slot (bucket) where the value is stored. A dict does exactly this: hash the key → get a slot number → grab the value straight from there.

Two keys, same slot: collisions

Sometimes two different keys hash to the same slot number — a collision. In coat-check terms it's two coats wanting the same hook. Don't panic: the hash table handles it (for example by keeping a small list at that slot, or probing for the next free slot). You don't have to worry about it — Python deals with it internally — just know that it can happen and gets resolved.

Quick check: dict lookup is O(1) but x in my_list is O(n) — why?
A list has no hash-to-slot mapping, so in must check items one by one until it finds a match — worst case the whole list (O(n)). A dict hashes the key and jumps straight to the slot, so it never touches most items — O(1).

Django bridge This is a real, common performance mistake. Say you have 50,000 allowed user IDs and on every request you write if user_id in allowed_ids. If allowed_ids is a list, each check is O(n) — up to 50,000 comparisons — and under high traffic it drags the view down. Turn it into a set (allowed_ids = set(allowed_ids)) and that same check becomes O(1), because a set is a hash table — just like a dict. The same trick is the fastest way to dedupe: unique = set(items). And the same idea powers, at scale, a database index (a direct lookup for a WHERE column instead of a full table scan) and Bloom filters (a hashing-based super-fast "maybe present / definitely not" check) — which you've already visited.
Quick check: what one-line change makes a membership check over 50k IDs fast?
Convert the list to a set: allowed_ids = set(allowed_ids). Now user_id in allowed_ids is O(1) instead of O(n) because a set is a hash table.

The tradeoff — name it in interviews Hash tables aren't free. Two costs: (1) more memory — the table keeps spare empty slots so collisions stay rare, so it uses more space than its items alone. (2) keys must be hashable, which usually means immutable — str, int, tuple are fine, but you can't use a list or dict as a key (that's why {[1,2]: "x"} raises an error). Speed in exchange for memory, plus "keys must be immutable" — naming both reads as senior.

Why is a dict lookup near-instant O(1) while in on a list is O(n)?
Your win today A hash table — behind dict and set — hashes the key to jump straight to the slot where the value lives, so lookup is O(1) instead of a list's O(n) scan. Collisions are handled for you. The cost: more memory and keys must be hashable/immutable. Practical: use a set for membership and dedupe — and remember the same idea powers database indexes and Bloom filters.
