Message queues: do the slow work later

How to keep requests fast by handing heavy jobs to background workers. Straight into your Celery world.

~9 min One concept: async work via queues Win: know what to move off the request

From memory: replication vs sharding — which is "copy" and which is "split," and which problem does each solve?
Replication = copy the whole DB → solves too many reads. Sharding = split the data across machines → solves data that's too big for one machine.

If you remember one thing A message queue lets a request drop a job in a line and return immediately, while a background worker does the slow part. The user isn't stuck waiting. This is "asynchronous" work.

The story: ordering food at a busy counter

At a good coffee counter, the cashier doesn't make your latte while you (and 20 people behind you) wait. They take your order, write it on a ticket, put it in the queue, hand you a buzzer, and serve the next customer. A barista works through the tickets and buzzes you when it's ready.

  • The cashier = your web request (stays fast, serves the next person).
  • The ticket rail = the message queue.
  • The barista = a background worker.
  • The buzzer = notifying the user when the job's done.

Without this, one slow order (a big report, sending 10,000 emails, encoding a video) would block everyone. The queue decouples the fast part from the slow part.

Django bridge — this is literally Celery You've likely used this: send_email.delay(user.id) in a Django view drops a task on a queue (Redis or RabbitMQ) and returns right away, so the user's request is fast. A Celery worker process picks it up and sends the email. Remember the GIL lesson (B1)? This is also the clean way to run CPU-heavy work — hand it to a separate worker process (its own GIL) instead of blocking your web server. Queues + workers = the standard Django answer to "this is too slow to do in the request."
Quick check: name two kinds of work you should move OFF the web request onto a background queue.
Any two: sending emails/notifications, generating reports or PDFs, image/video processing, calling slow third-party APIs, bulk data imports — anything slow or CPU-heavy that the user doesn't need to wait on.

One more idea: back pressure

Story: if orders pour in faster than the barista can make them, the ticket rail overflows and the whole shop gums up. So a smart shop, when swamped, says "we're at capacity, try again shortly" rather than accepting infinite orders it can't fulfill.

That's back pressure: when a queue grows dangerously long, the system pushes back — often returning an HTTP 503 (service busy) so clients retry later (ideally with growing waits, "exponential backoff"). It protects the system from drowning in its own backlog.

The tradeoff — name it Async isn't free. The job is now eventually done, not instantly — so the UI must handle "in progress" states, and you need to think about jobs that fail or run twice (make them idempotent — safe to repeat). You're trading instant simplicity for speed and resilience. Saying that tradeoff out loud is the senior move.

Your win today — and Week 1 is complete! 🎉 A message queue lets requests stay fast by handing slow/CPU-heavy work to background workers (exactly Django + Celery). Back pressure protects the system when the queue overflows (503 + retry). The cost: eventual completion, and you must handle retries/idempotency.
