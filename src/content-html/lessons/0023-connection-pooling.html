Connection pooling: borrow connections, don't build them

Opening a fresh database connection on every request is expensive — a pool keeps ready connections you borrow and return.

~8 min One concept: pooling Win: fix "too many connections"

30-second warm-up (recall N+1 queries)

From memory: what's the N+1 query problem, in one line?
One query fetches a list, then a query runs for each row — 1 + N round-trips to the database. The lesson there was that talking to the database is costly. Today we look at the very start of that: opening the connection itself is costly.
click to reveal — say it first
If you remember one thing Opening a new database connection is expensive (handshake + auth), and the database has a hard max-connections limit. A connection pool keeps a small set of ready connections — requests borrow and return them instead of building a new one each time. That's the whole idea.

Why opening a connection costs so much

  • TCP handshake: a network round-trip between app and database just to open the socket.
  • Auth: username/password check, TLS setup, permissions load — all once per connect.
  • Server-side memory: Postgres spins up a whole new backend process per connection. These aren't cheap.

All of that happens before the one query you actually wanted to run. Do it on every request and you've bolted pure setup cost onto every query.

The story: reserved desks in a reading room

Picture a library whose reading room has a fixed number of desks. In the old, silly way: every time someone comes to read, a carpenter shows up, builds a brand-new desk, and tears it down afterward. Each visitor waits 20 minutes for the build — the desk itself costs more than the reading.

The smart way: the library keeps desks ready in advance. You walk in, borrow a free desk, do your work, and return it on your way out so the next person can use it. No build time. And a hard rule: there are only so many desks — if they're all busy, you wait in line until one frees up.

Reading-room desks = database connections. The set of ready desks = the connection pool. Borrowing a desk = acquiring a connection; returning it on your way out = releasing it back to the pool.

At scale: "too many connections" Databases have a hard max-connections limit (Postgres default is often ~100). Now run 10 app servers, each opening its own pool of, say, 30 connections — that's 300, well past the limit. The database simply starts rejecting new connections, and you hit the famous production error: FATAL: sorry, too many clients already. Pools-per-server summing past the limit is the thing to name in interviews.
Django bridge By default Django opens a new DB connection at the start of each request and closes it at the end — connection-per-request, which is expensive. Set CONN_MAX_AGE (e.g. 60 seconds) so Django reuses persistent connections across requests instead of closing them — a small per-worker pool. But Django doesn't share connections across app servers, so at real scale people run PgBouncer — a separate pooler that sits in front of Postgres. All app servers talk to PgBouncer, and PgBouncer keeps a small, controlled set of connections to Postgres. This is the classic fix for the "too many clients" error.
Quick check: what does a pool save on every request that was wasted before?
The setup cost of a new connection: TCP handshake, auth/TLS, and spinning up a new backend process on the database. The pool hands over an already-open connection, so all that work is skipped and you go straight to the query.

The tradeoff: pool size (name it in interviews) Pool size is a Goldilocks number. Too small → all connections stay busy, requests wait for a free desk, latency spikes (and can time out). Too big → you blow past the database's max-connection limit or overwhelm it, and it starts refusing. The right size depends on total app workers, the DB's max_connections, and whether something like PgBouncer sits in front.

Your win today Connection pooling: opening a new DB connection is expensive (handshake + auth) and databases have a hard max-connections limit. A pool keeps ready connections that requests borrow and return — like reading-room desks. In Django: CONN_MAX_AGE for reuse, and PgBouncer in front at real scale. And you can now diagnose the too many clients already error on sight — plus name the pool-size tradeoff: too small = waiting, too big = overwhelm the DB.
