Safe database migrations: change the schema without downtime

Changing a live database's schema is risky — a bad migration can lock a big table and take the app down. The safe way: expand / contract.

~8 min One concept: expand/contract Win: migrate a live DB with zero downtime

30-second warm-up (recall table locks)

From memory: when a database locks a row or table, what happens to other queries?
They wait — they block until the lock is released. If the lock is held long (like rewriting a whole big table first), queries pile up, connections run out, and the app is effectively down. Remember: the bigger and longer the lock, the more dangerous.

If you remember one thing Never make a breaking change in one step on a live system. First make an additive, backward-compatible change (expand), then deploy code that tolerates both schemas, then backfill data, and ONLY then remove the old thing (contract). This is called expand / contract.

The story: renovating a busy restaurant while it's still open

Imagine you run a busy restaurant that needs a new, better kitchen. You don't knock down the old kitchen mid-service — otherwise every customer's food stops and the restaurant goes "down." Instead you do it cleverly:

  • Expand: build the new kitchen alongside the old one. Both exist at once. Nothing broke.
  • Switch over quietly: train the chefs to use both, then quietly route orders to the new one — customers never notice.
  • Contract: once everything runs off the new kitchen, remove the old one. It's safe now, because nobody's using it.

A database migration is exactly this. Old schema = old kitchen. Add the new thing first, run with both, move the data, then remove the old. Never "knock down a wall mid-service."

The concrete example: a NOT NULL column on a huge table

Say you have an orders table with 50 million rows, and you want a new status column that's NOT NULL with a default. If you do it in one step:

  • Bad: the database may have to write the default onto every row — that's a full table rewrite. It locks the table, and for 50M rows that can take minutes. Writes block that whole time — app down.

The safe way, in three small steps:

  • Step 1 (expand): add the column as nullable, no default. This is a metadata-only change — fast, no table rewrite, no lock.
  • Step 2 (backfill): fill in the value in batches (say 10,000 rows at a time) so no single long lock is held. The app keeps running meanwhile.
  • Step 3 (contract): once every row is filled, add the NOT NULL constraint. Now it only validates, doesn't rewrite — a small quick lock.
Django bridge Django bridge: in Django you run makemigrations (builds migration files from your models) then migrate (applies them to the DB). The catch: if a migration rewrites a big table (like adding a non-nullable column with a default, or changing a column type), Postgres takes an ACCESS EXCLUSIVE lock on that table — writes (and sometimes reads) block for as long as the migration runs. On a huge table that becomes an outage. The fix: split the same change into separate migrations — first a migration that adds the nullable column, then a data migration (RunPython) that backfills in batches, then a final migration that adds the constraint. And coordinate the deploy order: deploy code that works with both schemas (with or without the new column) before you run the contract step. That is, your code is always compatible with the DB, or ahead of it — never behind.
Quick check: why is adding a nullable column with no default fast, but adding a NOT NULL column with a default slow (locking)?
Nullable, no default = the database just changes the schema definition (metadata) — it doesn't touch existing rows, so no rewrite. NOT NULL with a default = every old row must now have that value, so the database has to (often) write every row — a full table rewrite that takes a lock. That's why we add nullable and backfill in batches.

Renaming and indexes: same pattern

  • Renaming a column: a one-step rename breaks any code still reading the old name. Instead: add the new column, write to both, backfill, switch code to the new one, then drop the old. Expand / contract again.
  • Adding an index: a normal CREATE INDEX locks the table for writes while the index builds. In Postgres, use CREATE INDEX CONCURRENTLY — it builds the index without locking the table (a bit slower, but no downtime).
The tradeoff: name it in interviews Multi-step (expand/contract) migrations are more work — three separate migrations instead of one big change, a backfill job, and deploy coordination. But they avoid downtime. On a new, small, or empty table a one-step big change is fine. On a large, live, high-traffic table, always expand/contract. The strong interview line: "I'd break this migration into backward-compatible steps so no long table lock is held — add nullable, batched backfill, then the constraint."
You need a new country column on an 80-million-row users table that must be NOT NULL. What's the safest approach on a live system?
In expand/contract, when do you deploy code that works with BOTH the old and new schema?
Your win today You can change a live database's schema with zero downtime: expand (an additive, backward-compatible change — nullable column, new column), deploy code that tolerates both schemas, backfill the data in batches, then contract (add the constraint / drop the old). You know that a NOT NULL-with-default on a big table triggers a table rewrite that locks writes — and in Django you split it into separate migrations and coordinate the deploy order. That's the "senior" move.
