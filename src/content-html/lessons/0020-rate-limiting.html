Rate limiting: capping how much each client can ask for

A simple guard that stops abuse and overload — and it connects straight to the DRF throttling you already use.

From memory: why do we reach for Redis as a cache, and why is it fast?
Redis keeps data in memory (not on disk), so reads/writes take microseconds. It's perfect for counters and short-lived keys. That same speed matters today — we'll keep per-client request counts in Redis so rate limiting stays fast.

If you remember one thing Rate limiting means: a client may only make so many requests per time window. Cross the limit and the server rejects the request — with HTTP 429 Too Many Requests. It protects your API from abuse and overload.

Why you need a rate limit

  • Stop abuse: keep one scraper or bot from hammering your API with thousands of requests a second.
  • Protect against overload: a traffic spike shouldn't drown your database and workers — the limit acts like a valve.
  • Fair usage: one loud user shouldn't eat all the resources and slow the API for everyone else.

The story: tokens at the chai stall

Picture a popular chai stall. To avoid chaos at rush hour, the owner keeps a bucket that gets filled with tokens — every minute he drops a few fresh tokens in, but the bucket has a max capacity (it never overflows). Each customer takes one token before ordering chai. Got a token? You get served. Bucket empty? "Come back in a bit" — request refused.

That's the token bucket algorithm. The bucket refills over time (a fixed rate), each request spends one token, and an empty bucket means 429. If someone pauses a moment the bucket refills — short bursts are allowed, but a sustained flood is not.

Fixed window vs sliding window (a small difference)

  • Fixed window: "100 requests per minute" — the counter resets to zero at each round minute. Simple, but abusable at the edge (100 at the end of one minute + 100 at the start of the next = 200 back-to-back).
  • Sliding window: counts the last 60 seconds as a moving window, so that edge-burst problem is smoothed out. A little more work, but fairer.
Django bridge You already use this in DRF — throttling. AnonRateThrottle limits anonymous users by IP, UserRateThrottle limits logged-in users by their user id. You set DEFAULT_THROTTLE_RATES in settings.py — like 'user': '1000/day'. Need it for non-DRF views? django-ratelimit gives you a decorator. And where do the counts live in production? In Redis — because every web worker must see the same shared counter (per-process memory won't do). When the limit is crossed, DRF sends 429 itself, often with a Retry-After header.
Quick check: what HTTP status does the server send on an empty token bucket, and what does it mean?
429 Too Many Requests. It means: "you crossed your allowed rate, try again shortly." Often a Retry-After header tells the client when to retry.

The tradeoff: name it in interviews Set the limit too strict and you block real users — a mobile app that fires 10 small calls from the previous screen hits 429 and breaks. Set it too loose and abuse and overload slip through — you lose the protection. The best limit lets normal traffic pass comfortably and only stops abusive spikes. That's why you set per-endpoint and per-user-tier limits, not one global number.

Your win today Rate limiting: give a client only so many requests per time window; cross the limit = 429. The mental model is the token bucket — it refills over time, each request spends a token, an empty bucket rejects (short bursts fine, floods not). Fixed vs sliding window is just how you count. In Django it's DRF throttling, with counts in Redis. And that tradeoff — too strict blocks real users, too loose lets abuse in — is worth naming in an interview.
