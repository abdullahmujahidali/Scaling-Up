IAM policy evaluation: Deny always wins

This is the easiest point on the exam. The rule is one line long, and a question on it appears almost every time. These are free marks — you only have to know the rule.

~7 min One concept: how AWS decides allowed or denied Win: a guaranteed exam question
Recall from A3: the table is in production and you need to query a new attribute — LSI or GSI, and why?
GSI. L = Local = Locked — an LSI is only creatable with the table. The table already exists, so that option is dead.

If you remember one thing Explicit DENY > Explicit ALLOW > Implicit deny (the default).

Meaning: if Deny appears anywhere — in even one policy — the answer is always "access denied". Even if ten other policies say Allow. And anything not mentioned at all is also denied — because AWS's default is no.

The story: the building's security guard

Imagine an office building with one security guard. He has three lists:

  • The "do not admit" list (Deny). He checks this first. If your name is on it — that's it, finished. Even if you carry a permission letter from the CEO, even if your name is also on the "admit" list. For the guard, this list outranks everything.
  • The "admit" list (Allow). Not on the deny list? Now he checks this one. Name found → you go in.
  • Name on neither list (implicit deny). The guard says "I don't know you" — and doesn't let you in. That's the default. AWS works identically: anything not explicitly allowed is denied.

That's the entire rule. The exam asks it like this: it shows three policies and asks "can the user do this?" — and your only job is to hunt for a Deny. Found one → the answer is no, whatever the rest say.

Parts of a policy — this is enough to read the question

PartMeaning
EffectAllow or Deny. ⭐ Look at this first.
ActionWhich operation — e.g. s3:GetObject, dynamodb:PutItem. * means everything.
ResourceOn what — written as an ARN. Note: bucket and bucket/* are different things (the bucket itself vs the objects inside it).
ConditionWhen it applies — e.g. only from this IP, or only with MFA. If the condition isn't met, that statement simply doesn't apply.
Trap — role vs user Nearly every security question includes an option that stores an access key somewhere — an environment variable, an encrypted file, a config file. They are all wrong. The right answer is almost always an IAM role, because a role hands out temporary, auto-rotating credentials — there's no permanent key to steal. Remember: the question isn't "where do we hide the key"; the right answer is "don't have a key at all".
Exam English — words in security questions "explicit" = written out plainly. "implicit" = not written, understood by default. "least privilege" = only as much permission as needed, not a scrap more — AWS's favourite principle. "assume a role" = temporarily take on a role's permissions (here "assume" means take on, not guess). "temporary credentials" = a key that expires by itself.

Bridge to your Django work Django permissions work the same way. When you add @permission_required and the user lacks it, Django refuses — however many other permissions they hold. That's implicit deny: what wasn't granted doesn't exist. And the access-key vs IAM-role distinction is exactly your hard-coded SECRET_KEY in settings.py versus reading it from the environment — except AWS goes one step further: with a role there is no permanent secret at all, so there's nothing left to steal.
