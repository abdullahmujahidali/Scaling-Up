If you remember one thing The root user is the owner who can do everything — which is exactly why you don't use it day to day.

The exam's favourite answer is always:
1. Enable MFA on the root user.
2. Delete root's access keys.
3. Create an IAM user/role for everyday work.
4. Give everyone only the access they need — this is called least privilege.

⭐ And a heavily tested rule: to give EC2 or any AWS service access, always use a ROLE — never access keys in code.

The story: office keys

Imagine you own an office. The root user is the master key that opens every lock, including the safe. You don't carry it around daily — you lock it away and put an extra lock on it (MFA).

IAM users are your employees, each with their own key. IAM groups are departments — everyone in "accounts" gets the same key, rather than issuing each separately. IAM policies are the written rules of which key opens which door.

And an IAM role? That's a visitor badge worn temporarily. No employee, no permanent key — access lasts while the badge is worn. You give an EC2 instance a badge, not a key — because keys get lost (leaked in code), while badges expire on their own.

⭐ IAM — what definitely gets asked
  • ⭐ Only the root user can: close the account, change account settings/email, change the support plan, and control billing access. "Only the root user can…" refers to these.
  • ⭐ IAM Role = temporary, self-expiring permission. Giving EC2, Lambda or any service access = a role. User = for a person. Group = a collection of users (attach policies to the group, not to each user).
  • ⭐ MFA (multi-factor authentication) = password plus a second factor (a phone code). "An extra layer of security for sign-in" = MFA.
  • ⭐ Least privilege = grant only the permissions required, nothing more. AWS's central security principle and frequently the correct answer.
  • IAM Identity Center (formerly AWS SSO) = single sign-on across many AWS accounts. Federation = signing in with an existing identity (company Active Directory, Google) without creating new IAM users.
  • Secrets Manager = storing passwords and API keys securely (with automatic rotation). Systems Manager Parameter Store = storing configuration and secrets, the cheaper option.
⭐ The security services — one job each
  • ⭐ AWS WAF (Web Application Firewall) = protection from web attacks — SQL injection, cross-site scripting. "Protect a web application from common exploits" = WAF.
  • ⭐ AWS Shield = DDoS protection (floods of traffic trying to take a site down). Shield Standard is free and automatic; Shield Advanced is paid. "DDoS" in a question = Shield, always.
  • ⭐ Amazon GuardDuty = threat detection — spots suspicious activity by analysing logs automatically. "Detect malicious or unusual activity" = GuardDuty.
  • ⭐ Amazon Inspector = finding vulnerabilities — outdated or flawed software in EC2 instances and container images. "Scan for vulnerabilities" = Inspector.
  • ⭐ Amazon Macie = discovering PII / sensitive data in S3.
  • AWS Security Hub = one dashboard for all security findings. Amazon Detective = investigating an issue (why it happened). AWS Firewall Manager = managing firewall rules across many accounts.
  • ⭐ AWS KMS (Key Management Service) = creating and managing encryption keys. CloudHSM = the same on dedicated hardware (for strict compliance). ACM = SSL/TLS certificates for HTTPS, free.
  • ⭐ AWS Artifact = where you download AWS's compliance reports (SOC, ISO, PCI). "Where do I obtain AWS's compliance documentation" = Artifact, always.
The pairs that get confused Inspector vs GuardDuty: Inspector finds weaknesses (outdated software, open settings) — "the door is weak". GuardDuty catches attacks (suspicious activity happening now) — "someone is at the door".

WAF vs Shield: WAF = clever attacks (SQL injection — one malicious request). Shield = brute-force attacks (DDoS — millions of requests to knock you over).

CloudTrail vs CloudWatch: CloudTrail = who did what (audit, API calls). CloudWatch = how the system is doing (metrics, logs, alarms). This pair appears on every exam.

Config vs CloudTrail: Config = what state is it in and when did that change (configuration history). CloudTrail = who changed it.
Exam English — security vocabulary "least privilege" = the minimum permission necessary.
"credentials" = sign-in items (username/password, access keys).
"federated" = signing in via an external identity system.
"at rest" / "in transit" = stored data / moving data. Both should be encrypted — often the correct answer.
"exploit" = to take advantage of a weakness.
"malicious" = intentionally harmful.
"audit" = an inspection record.
"compliance" = meeting legal or industry rules.
"mitigate" = reduce a risk.
"rotate" (keys/secrets) = replace them periodically.

Bridge to your Django work Least privilege is the principle behind your Django permissions. You don't make every user a superuser — you create groups and grant only what's needed. IAM is the same idea over AWS resources: IAM group = Django group, IAM policy = permissions.

The role vs access keys decision you already know: you don't hard-code the database password in settings.py — it comes from the environment or a secrets manager. Keys in code is that same mistake. A role goes one better: there's no key at all, so nothing can leak.

And the root user? That's your postgres superuser. You don't connect the app with it — you create a dedicated user scoped to one database.
From memory: two steps to protect root? The right way to give EC2 access to S3? Inspector vs GuardDuty? DDoS = which service? Where do compliance reports come from?
Root: enable MFA + delete access keys (and use an IAM user daily). EC2 → S3 = an IAM role (never keys). Inspector finds weaknesses; GuardDuty catches attacks. DDoS = AWS Shield. Compliance reports = AWS Artifact. All five? Then Domain 2's 30% is in hand.
