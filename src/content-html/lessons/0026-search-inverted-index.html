How search works: the inverted index

Why real search isn't LIKE '%word%' — and the little trick that makes a word an instant lookup.

Instead of scanning the whole table, an index keeps a sorted lookup (like the index at the back of a book), so "where is this value" becomes a jump, not a read of every row. Today we stretch that same idea to search — but word → documents.

If you remember one thing Real search uses an inverted index: flip your thinking from "document → its words" to "word → the list of documents that contain it". Now finding a word is an instant lookup, not a read of every document.

First: why LIKE '%word%' isn't enough

It looks easy — the user types "mango" in the search box, you run WHERE body LIKE '%mango%'. It works on small data. But it has three problems:

  • Slow: the leading % forces the database to scan the full text of every row — no index is used. A million rows = a million reads.
  • Dumb matching: search "running" and it won't match "run"; "colour" and "color" differ; a substring "man" accidentally matches inside "human".
  • No ranking: you just get rows back — no sense of which result is more relevant. The whole point of search is putting the best result on top.

The story: a book's index vs reading the whole book

Imagine you have a 900-page textbook and you need to find "photosynthesis". Two ways:

  • The LIKE way: start at page 1 and read every page until you spot the word. Every single time. That's a full scan.
  • The index way: flip to the index at the back of the book. It says photosynthesis → 88, 214, 560. You jump straight to those pages. An instant lookup.

Someone did the work ahead of time: they read the whole book and wrote each important word next to its page numbers. That "word → page numbers" mapping is an inverted index. A search engine builds exactly this — just "document IDs" instead of "page numbers".

Quick check: what exactly gets "inverted"? What was the original mapping, and what's the new one?
Original: document → the words inside it. Inverted: word → the list of documents that contain that word. That's why searching a word is a direct list lookup, not a scan of every document.

And how the best result reaches the top (ranking)

Getting the matching documents for a word is half the job. The other half: ranking — which result is most relevant. A search engine looks at things like how often the word appears in a document, how rare that word is overall, and whether it's in the title or the body — then scores results so the best one floats to the top. Grasp it abstractly for now; the actual formulas (TF-IDF, BM25) are their own lesson.

Django bridge Django gives you full-text search inside Postgres — no separate server. SearchVector breaks your text into searchable tokens (this feeds the inverted index), SearchQuery parses the user's query, and SearchRank gives you ranking: Article.objects.annotate(rank=SearchRank(SearchVector('title','body'), SearchQuery('mango'))).order_by('-rank'). For speed you add a SearchVectorField + a GIN index so it isn't recomputed each time. This is great for moderate scale. When data gets huge or you need fancy relevance, fuzzy matching, autocomplete, and facets — people reach for a dedicated engine (Elasticsearch / OpenSearch), which does this same inverted-index idea at industrial scale.
The tradeoff — name it in interviews A search index must be kept in sync with your data: every write (add / edit / delete) must update the index, or search goes stale. Inside Postgres you do this with a trigger or a stored SearchVectorField. With a separate engine (Elasticsearch) you have to ship writes over to it (often via a queue / background job) — which becomes a whole second system to run, monitor, and back up. That operational complexity is the real cost — reach for Postgres FTS first, until you genuinely need more.
