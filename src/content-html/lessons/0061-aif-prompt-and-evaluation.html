Prompt engineering, customisation and evaluating models

This is AIF's largest domain. In I1 you learned RAG vs fine-tuning — now the detail: prompting techniques, every route to customising a model (and what each costs), and how to tell whether a model is actually working.

From I3: what is prompt injection? The commonest cause of bias? And the real cure for hallucinations?
Prompt injection = hidden user instructions hijacking the model (the SQL-injection instinct). Bias comes from the training data. Hallucinations are cured by RAG grounding + output validation + human review. Today we go further: the craft of prompting, and how to judge a model.

If you remember one thing There are four routes to customising a model — and the exam always asks for the CHEAPEST one that meets the need. In cost order (cheapest first):

1. Prompt engineering — just ask better. No training. Cheapest.
2. RAG — show it your documents. The model is unchanged.
3. Fine-tuning — retrain the model on your data. Expensive.
4. Pre-training from scratch — millions of dollars. Almost always the wrong answer on this exam.

⭐ The rule: start at the top and only move down when you must. If a question says "lowest cost" or "least effort", the answer is as high up that list as will work.

The story: briefing a new employee

The same employee from I1. There are four ways to get them doing your work, and you always pick the cheapest that suffices:

1. Give clearer instructions: "write this report, three paragraphs, formal tone" — that's prompt engineering. Free and instant. 2. Hand them the company files to work from — RAG. 3. Send them on weeks of training so they write in your house style — fine-tuning. Expensive, but the manner genuinely changes. 4. Or raise a person from childhood — pre-training. Nobody sensible does this without an extraordinary reason.

⭐ Prompting techniques — these names get asked
  • ⭐ Zero-shot = no examples given, just the instruction. ("Classify the sentiment of this review.")
  • ⭐ Single-shot / one-shot = one example given. Few-shot = several examples given. Examples make responses better and more consistent. "Provide a few examples in the prompt" = few-shot.
  • ⭐ Chain-of-thought = telling the model to reason step by step. Markedly better on maths and logic tasks. "Complex reasoning" or "step by step" = chain-of-thought.
  • Parts of a prompt: instruction (what to do), context (background), input (the data), output format (the shape of the answer). A negative prompt says what not to do. A prompt template is a reusable structure with the data swapped in.
  • Risks of prompt engineering (named in the exam guide): exposure (secrets leaking via prompts), poisoning (feeding corrupt data), hijacking and jailbreaking (pushing the model past its limits). Bedrock Prompt Management = storing and versioning prompts.
⭐ Inference parameters — the knobs that change output
  • ⭐ Temperature = how random or creative the output is. Low temperature (near 0) = consistent, predictable, safe — for facts and calculations. High temperature = more varied and creative — for story writing. ⚠️ Temperature does NOT fix hallucinations — a common exam trap.
  • Top-p (nucleus sampling) and Top-k = also control variety, like temperature. Max tokens / output length = how long the response may be — and it directly affects cost.
  • Context window = how much text the model can consider at once (prompt + response). It matters for large documents. Prompt caching = caching the repeated portion of prompts to save cost and latency.
  • ⭐ Criteria for choosing a model (from the exam guide): cost, modality (text/image/audio), latency, multilingual support, model size, how customisable it is, and input/output length.
⭐ Evaluating a model — the metric names
  • ⭐ ROUGE = evaluating summarisation. BLEU = evaluating translation. This pair gets asked — ROUGE = summaries, BLEU = translation.
  • BERTScore = similarity by meaning, not just words. LLM-as-a-judge = using one model to grade another's output. Human evaluation = people judging directly — most trustworthy, but slow and costly.
  • ⭐ Traditional ML metrics (from Domain 1, but they appear here too): Accuracy = how many predictions were right. Precision = of those flagged "yes", how many truly were (avoiding false alarms). Recall = of those that truly were, how many we caught (avoiding misses). F1 = the balance of the two.
    Memory hook: detecting disease or fraud → Recall matters (missing a case is unacceptable); a spam filter → Precision matters (real mail must not be binned).
  • Amazon Bedrock Model Evaluation = AWS's tool for evaluating models (automatic and human). Benchmark datasets = standard test sets.
    Business metrics the exam lists: task completion rate, user satisfaction, cost per interaction, ROI.
Fine-tuning detail — when it genuinely is the answer
  • Instruction tuning = training the model to follow instructions. Domain adaptation = teaching a specialist field's language (medical, legal). Continuous pre-training = further training on your unlabelled data. Transfer learning = reusing what was learned for one task on another.
  • RLHF (Reinforcement Learning from Human Feedback) = improving a model using human preference judgements. This is how models are made "helpful".
  • Data required for fine-tuning: curated (selected and cleaned), labelled, representative of the real world, sufficient in size, and governed (known provenance). Fine-tuning on poor data makes things worse.
  • Model distillation = producing a smaller, cheaper model from a large one that performs nearly as well. "Reduce inference cost while keeping quality" = distillation.
Exam English — Domain 3 vocabulary "shot" (zero-shot, few-shot) = an example. "Few-shot" = with a few examples.
"inference parameters" = settings applied when generating (temperature and so on).
"deterministic" = the same result every time (low temperature). "nondeterministic" = varies each time.
"concise" = short and to the point.
"curated" = deliberately selected and prepared.
"benchmark" = a standard to measure against.
"latency" = delay before a response.
"throughput" = how much work per unit time.
"distillation" = condensing into something smaller.
"grounding" = anchoring answers in real source material.

Bridge to your work Think of temperature as ORDER BY RANDOM() in a query. For a report you never want randomness — you want the same result every run. The financial assistant wants the same: temperature 0.

Few-shot prompting is what you do when explaining your PR format to a new developer: you don't hand them a rulebook, you say "write it like these two past PRs". Two examples land better than a whole document.

And precision vs recall? That's your test suite trade-off. A false positive is a test failing for no reason (annoying). A false negative is a bug slipping through a passing test (dangerous). Which you fear more depends on what the system does — exactly the difference between the hospital and the spam filter.
