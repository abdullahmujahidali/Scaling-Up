Webhooks: "don't call us, we'll call you"

Normally your app calls an external API. A webhook flips it — the external service calls you when something happens.

~8 min One concept: webhooks Win: stop polling, get pushed to

30-second warm-up (recall idempotency — B6)

From memory: what does idempotency mean, and why does a retry-heavy system need it?
Idempotent = run the same operation once or ten times, the result stays the same (no double charge, no duplicate row). Retry-heavy systems need it because if the sender loses your response it sends the same request again — you must handle that duplicate safely. Today we'll see why this applies directly to webhooks.

If you remember one thing Polling = you keep asking "is it done? is it done?". A webhook = you hand over your URL and the service sends you an HTTP POST when the thing happens. You stop asking; it pushes to you.

The story: ordering a cake at the bakery

You order a cake at the bakery. There are two ways to find out when it's ready:

  • Polling: you walk to the counter every 5 minutes and ask "is my cake ready?" "Now?" "Now?" Most of the time the answer is "not yet." You waste your time and theirs.
  • Webhook: you hand them your phone number and go home. When the cake is ready, they call you. One call, at exactly the right moment, no wasted trips.

Remember the bakery's rule: "don't call us, we'll call you." That's a webhook. Your phone number = your public URL. Their call = an HTTP POST arriving at your URL carrying the event details ("cake #42 ready", or "payment succeeded").

Django bridge A webhook receiver is just a Django view with a public URL — Stripe, GitHub or Twilio POST to it when a payment succeeds, code is pushed, or an SMS arrives. Four things every production webhook view does: (1) verify the signature — anyone can POST to your URL, so check an HMAC header against the sender's secret or you'll accept forged events. (2) Return 200 fast — the sender gives a short timeout; if you do heavy work inside the request it'll time out and retry. (3) Do the work async — hand the event to a Celery task and respond immediately. (4) Handle duplicates — when the sender misses your response it resends the same event, so dedupe on the event id with a unique constraint/lookup. That last point is idempotency (B6) you just recalled.
Quick check: why shouldn't your webhook view do the heavy work (send email, update DB) inside the request itself?
Because the sender (Stripe, GitHub) has a short timeout — if you don't return 200 quickly it assumes delivery failed and sends a retry (piling up duplicates). So: verify, push the work to Celery, return 200 immediately. The heavy work happens in the background.

The tradeoff — name it in interviews A webhook cuts latency and waste versus polling, but the price is: you must expose a public endpoint and secure it (signature verification, or anyone can push forged events), and you must accept that the sender will retry — meaning duplicate events. That's exactly why webhook receivers must be idempotent. "Verify the signature, respond fast, process async, dedupe on event id" is the four-word senior signal.
Your Django payment view takes a webhook POST from Stripe, sends the customer an email and generates an invoice inline (takes 3 seconds), then returns 200. Stripe keeps resending the same event again and again. What should you fix first?
An attacker found your public webhook URL and sent a fake "payment succeeded" POST there. What stops you from accepting it?
Your win today Webhooks flip polling around: instead of asking repeatedly, the service pushes you an HTTP POST when an event happens — "don't call us, we'll call you." In Django that's a public view doing four jobs: verify the signature, return a fast 200, do the work async on Celery, and dedupe on the event id. That last job is idempotency — which is why the two lessons connect.
