Observability: when your system is live and something breaks, how do you SEE it?

Three pillars — logs, metrics, traces. You can't fix what you can't see.

From memory: when does a circuit breaker trip "open", and how does it even know?
When a downstream service keeps failing (error rate crosses a threshold), the breaker goes open and stops calls. But notice — first it has to count the error rate. That "error rate" is a metric. Today we learn the whole ecosystem for seeing and measuring that data properly.

If you remember one thing Observability has three pillars: LOGS (what happened — detailed text records), METRICS (how much / how fast — numbers over time), and TRACES (where one request went — its journey across services). Together they give you "eyes" into a live system.

The three pillars

  • Logs — "what happened": detailed text records of individual events. User 42 logged in, Payment failed: card declined. When you want to know exactly what happened at which line, you read logs.
  • Metrics — "how much / how fast": numbers over time. Request rate (requests per second), error rate, latency (how long it took), CPU, memory. These get graphed and trigger alerts.
  • Traces — "where did the time go / where did it fail": follow ONE request as it hops from service to service. Web app → auth service → database → payment API. The trace shows how long each hop took and where it broke.

A good mental hook: logs are zoomed in (one event), metrics are zoomed out (whole-system health), and traces are horizontal (one request's journey).

The story: running a restaurant

Imagine you run a busy restaurant, and one night customers complain that "service is slow." You have three ways to see what's going on — exactly like the three pillars:

  • Logs = the order tickets: the detailed slip for each order — what was ordered, at what time, from which table. If a dish went wrong, you find and read that exact ticket. It's the full story of one event.
  • Metrics = the dashboard on the wall: "tables served per hour", "average wait time", "kitchen busy %". One glance tells you tonight is slower than normal — without reading a single ticket.
  • Traces = following one specific customer's whole journey: door → seat → order → kitchen → served → bill. You walk with ONE particular customer and see where the time was lost — "the order sat in the kitchen for 20 minutes." That's the bottleneck.

The dashboard (metrics) tells you something is wrong. Traces tell you where. And the order tickets (logs) tell you exactly what. You need all three.

Django bridge All three are already within reach in your Django stack. Logs: Python's built-in logging module — logger.info(), logger.error() — and prefer structured logs (JSON) so machines can search them. Error tracking: Sentry catches every exception with its traceback. Metrics: Prometheus scrapes numbers (request rate, latency) and Grafana graphs them. Traces: OpenTelemetry follows one request across a Django view → Celery task → external API call — so you can see whether that slow request lost its time in Celery or in a third-party API.
Quick check: users say "checkout is slow". Which pillar first tells you where the time is being lost — auth, database, or the payment API?
Traces. A trace follows one checkout request across every hop and shows each step's timing, so you immediately see the bottleneck is the payment API (not your database). Metrics alerted you that "latency is up"; logs will later give the exact error line.

The tradeoff: measuring everything is expensive and useless Instrumentation is not free — every log line, metric, and trace costs CPU, network, and storage, and adds a little runtime overhead. Worse: if you log everything, the signal drowns in noise — finding the one real error inside 10,000 useless lines becomes impossible. So senior engineers choose WHAT to measure: key metrics, meaningful log levels, and sampled traces of only important requests. Name it in an interview: "observability's cost is overhead and noise, so I deliberately choose what to instrument."
An alert is firing: "error rate jumped from 1% to 12% over 5 minutes." This signal — a number over time — is which observability pillar?
A user's checkout request takes 8 seconds. You want to see EXACTLY where those 8 seconds went — across the Django view, a Celery task, or the payment API. What do you reach for?
Your win today The three pillars of observability: logs (what happened — detailed events, like order tickets), metrics (how much/how fast — numbers over time, like the wall dashboard), and traces (where the time went — one request's journey, like following a customer). In Django: logging+Sentry, Prometheus+Grafana, and OpenTelemetry. And you know the tradeoff — measuring everything is expensive and noisy, so choose deliberately. You can't fix what you can't see — and now you know how to see.
