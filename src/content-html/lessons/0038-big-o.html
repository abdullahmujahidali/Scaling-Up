Big-O notation: how we measure speed

Big-O isn't about exact time — it's about how the work grows as your data grows. It's about scaling.

~8 min One concept: growth rate Win: know when your code won't scale

30-second warm-up (recall indexes & N+1)

From memory: why does a database index make a lookup fast? And what is an N+1 query?
An index is a sorted structure — the database jumps straight in instead of scanning every row. An N+1 is when you fetch a list with 1 query, then run 1 more query per item — 1 + N queries. Today we'll see the real reason behind both: it's all about growth rate.

If you remember one thing Big-O describes how fast the work grows as the input (n) grows — not exact seconds, just the shape. On small data everything works; on big data O(n²) code dies while O(log n) barely notices.

The story: finding one person

Imagine a huge stadium, and the goal is to find one specific person. How much work that takes depends entirely on how you look:

  • O(1) — constant: someone hands you the number directly. Whether the stadium holds 100 people or 100,000 — the work is identical. Like looking up your seat number: instant, no matter how big the stadium.
  • O(log n) — logarithmic: the people are sorted, so you keep halving. Like finding a name in a phone book — open the middle, decide which half, repeat. Double the book and it adds just one extra step. Wildly scalable.
  • O(n) — linear: you ask every person one by one. Twice the people = twice the work. Like checking every seat one at a time.
  • O(n log n) — good sorting: sorting the whole stadium by name using a smart method. A bit more than O(n), but far better than O(n²). Most fast sorts are this.
  • O(n²) — quadratic: every person shakes hands with every other person. 10 people = 100 handshakes; 1,000 people = 1,000,000 handshakes. It explodes. Like comparing everything to everything.

Notice what happens when you double n: O(1) doesn't move. O(log n) adds one step. O(n) doubles. O(n²) becomes four times bigger. That's the whole story.

Django bridge This shows up in your code daily. A dict or set lookup — user_id in my_set — is O(1); instant. But x in my_list on a list is O(n) — Python scans every element. Need a big membership check? Build a set. Next: an accidental nested loop inside a queryset (looping every product for every order) is O(n²) — that's exactly why N+1s and nested loops die so fast at a few thousand rows. And that index? A database WHERE email = ... without an index is an O(n) full scan; with an index it's O(log n) (a sorted B-tree, keep halving). That's why an index matters once the table gets big.
Quick check: you often check "is this ID present?" in a large list. What small change makes it O(1) instead of O(n)?
Put that list into a set (or dict). x in some_list is O(n) (scans every element); x in some_set is O(1) (hash lookup). One-line change, big difference as data grows.

The tradeoff — name it in interviews On small data anything works — O(n²) on 50 items is nanoseconds, don't over-optimize it. Big-O hides constant factors: a simple O(n) loop often beats a fancy O(log n) trick when n is tiny. The real skill is knowing when your approach won't scale — when n could reach thousands/millions, O(n²) is a time-bomb. So ask: "how big can this get?" and decide from that.
You loop over a list, and for each item you loop over the same list again to compare every pair. What's its time complexity?
To find a name in a sorted phone book you keep halving. Doubling the phone book adds just one extra step. Which growth rate is this?
Your win today Big-O: the growth shape of work as data grows. O(1) seat number, O(log n) phone-book halving, O(n) asking everyone, O(n log n) good sorting, O(n²) every-pair handshake (explodes). In Python: set/dict lookup O(1), list in O(n), nested queryset loop O(n²), indexed DB lookup O(log n). Don't over-optimize tiny data — but know when your approach won't scale. Saying "this is O(n²), it won't hold at large input" in an interview is a strong senior signal.
