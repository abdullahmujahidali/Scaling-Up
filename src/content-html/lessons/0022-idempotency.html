Idempotency: do the same thing twice, get the same result

The one trick that stops retries and double-clicks from charging the customer twice.

~8 min One concept: idempotency Win: make retries safe

30-second warm-up (recall HTTP methods)

From memory: what's the difference between GET, PUT, and POST in REST design?
GET reads data, changes nothing. PUT replaces/updates a resource at a known ID. POST usually creates something new (a new order, a new row) — the server assigns the ID. This distinction is about to matter.

If you remember one thing An operation is "idempotent" if running it once or five times leaves exactly the same result as running it once. That's what makes retries and double-clicks safe.

The story: the elevator button

You're waiting for the elevator and you're late. You press the "up" button. Nothing happens, so you press it five more times, then twice more out of frustration. What does the elevator do? The same thing it did on the first press — one elevator arrives. Pressing the button five times equals pressing it once. You haven't ordered yourself five elevators.

That's idempotency. Now map it to a payment: a customer presses "Pay", the page hangs, they angrily press it again. If your server treats each click as separate, you just charged them twice. If your server behaves like the elevator button, it charges once — no matter how many times they press.

Quick check: is a double-click the only way a request gets sent twice, or are there other causes?
Many more: on a network timeout the client retries (even though the first request already reached the server), a mobile app resends when a connection drops, a load balancer retries, or a Celery task re-runs after a perceived failure. A human double-click is just the easiest example.

Which methods are already idempotent

MethodIdempotent?Why
GETYesReads only — nothing changes, ever
PUTYesSets a resource to a value; setting it twice = same value
DELETEYesDeleting an already-deleted thing leaves it deleted
POSTUsually notEach call tends to create a new row / new order / new charge

The problem is almost always POST — because that's what creates something new. "Create a payment", "place an order", "send money" — these are all POSTs, and running them twice creates two payments, two orders, two transfers. That's the one we need to fix.

The fix: idempotency keys

The idea is simple: the client sends a unique key with each request (a random UUID, generated once). The server remembers that key. If the server sees the same key again, it does not re-run the operation — it just returns the result from the first time.

  1. The client generates a key, e.g. Idempotency-Key: 7f3a-91c2-..., and sends it with the POST.
  2. The server checks: "have I seen this key before?" If not — process the payment, store the result against that key.
  3. If it sees the same key again (retry, double-click) — do not charge again. Return the same stored response.
Django bridge If you use Stripe, you've already seen this: send an Idempotency-Key header on each charge request, and Stripe guarantees the same key won't repeat the charge — it returns the original response. You can build the same in your own APIs: a small table IdempotencyKey(key, response, created_at), or Redis with SET idem:<key> <result> NX EX 86400. Before processing the payment, check the key — if it exists, return the stored result and stop. In Postgres a unique constraint on the key column is a second safety net: inserting the same key again raises an IntegrityError, which you catch and return the existing record. This is why making Celery tasks and DRF endpoints idempotent makes retries so much calmer.
Quick check: who generates the idempotency key — the client or the server? And why?
The client generates it (once, before sending) and resends the same key on retries. If the server generated it, every retry would carry a new key and the server would have no way to recognize it — the whole point is that one "logical" request has one stable key that can travel the network multiple times.

The tradeoff — name it in interviews Idempotency isn't free: you have to store every key and do a lookup before processing the payment. That's a little extra storage and one extra database/Redis hit per request. But in exchange you prevent double charges, duplicate orders, and repeated money transfers — real money and real trust. The trade is: a bit of storage + one lookup, in exchange for avoiding disasters that genuinely hurt customers. For any payment or "create" endpoint, that trade is always worth it.
