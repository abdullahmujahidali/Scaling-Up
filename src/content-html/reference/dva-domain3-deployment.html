The heart of this domain Two things cover most of the questions: (1) Infrastructure as Code — CloudFormation and its serverless little brother SAM. (2) Deployment strategies — what happens to existing users when you ship a new version. Everything else (CodePipeline, Beanstalk, ECS) orbits these two.

1. Deployment strategies — the most-asked topic

A restaurant analogy: you must replace the old menu with a new one. You have four ways — and the exam asks which one when.

StrategyWhat happensDowntime / costTrigger words
All-at-once Replace everything at once. Throw out the old menu, put up the new one. HAS downtime. Cheapest and fastest. "FASTEST", "dev environment", "downtime acceptable"
Rolling Replace in batches — 2 tables, then the next 2. Both menus run for a while. No downtime, but reduced capacity during the roll. No extra servers needed. "no additional cost", "gradual"
Blue/Green Build a whole second restaurant (green), test it, then send all customers over at once. The old one (blue) stays standing. Zero downtime. Rollback is INSTANT (send traffic back to blue). But DOUBLE cost while both run. ⭐ "zero downtime", "instant/fast rollback", "minimize risk"
Canary Give the new menu to just 10% of customers. Watch for complaints. If fine, roll out to the other 90%. Zero downtime, lowest risk, but slowest. ⭐ "small percentage of users first", "test in production", "gradual traffic shift"
Blue/Green vs Canary — remember the difference Both are zero-downtime and both appear together as options. The difference: Blue/Green switches 100% of traffic at once (0% → 100%). Canary shifts traffic gradually (10% → 50% → 100%). If the question mentions "a small percentage of users" or any percentage → Canary. If it says "switch all traffic" or "instant rollback" → Blue/Green.

Lambda's own deployment options (via CodeDeploy)

  • Canary10Percent5Minutes — 10% of traffic for 5 minutes, then the rest.
  • Linear10PercentEvery1Minute — add another 10% every minute.
  • AllAtOnce — everything immediately.
  • These all work via Lambda aliases. An alias is a pointer to a version (e.g. PROD → version 7). Traffic shifting means the alias splits traffic between two versions.

2. CloudFormation and SAM

CloudFormation is a recipe. You write "I want 2 EC2 instances, 1 database, 1 load balancer" — and AWS builds it. Change the recipe and AWS works out the difference and changes only what's needed. Delete it and everything is cleaned up.

Template sections

  • Resources — ⭐ the ONLY required section. Everything else is optional.
  • Parameters — inputs at deploy time (e.g. environment name).
  • Mappings — fixed lookup tables (e.g. AMI ID per region).
  • Outputs — values other stacks can import.
  • Conditions — create some resources only in certain cases (e.g. prod only).
CloudFormation concepts you need
  • Change Sets — show what WILL change before you deploy. "Preview changes before applying" = Change Set.
  • Drift detection — tells you someone changed something manually in the console that no longer matches the template.
  • StackSets — deploy one template across MANY accounts and MANY regions.
  • Nested stacks — break a big template into smaller reusable pieces.
  • DeletionPolicy: Retain — keeps a resource (like a database) even when the stack is deleted. "Don't lose the data" = DeletionPolicy Retain.
  • Rollback: if a create/update fails, CloudFormation automatically reverts to the previous state.

AWS SAM — CloudFormation shorthand for serverless

  • SAM extends CloudFormation. The template begins with Transform: AWS::Serverless-2016-10-31 — that line identifies SAM, and the exam asks about it.
  • Resource types: AWS::Serverless::Function, ::Api, ::SimpleTable. These compress 20 lines of CloudFormation into 5.
  • Commands: sam build → sam package (upload artifact to S3) → sam deploy. sam local invoke / sam local start-api test locally (needs Docker) — this is task statement 1.1.7.

3. CI/CD services — who does what

ServiceJob
CodeCommitGit repository (AWS's own GitHub). Closed to new accounts now, but still on the exam.
CodeBuildCompiles code and runs tests. Instructions live in buildspec.yml (at the repo ROOT).
CodeDeployDeploys code to EC2/Lambda/ECS. Instructions in appspec.yml.
CodePipelineThe orchestrator — chains everything in order (source → build → test → deploy).
CodeArtifactPackage repository (private storage for npm, pip, Maven).
Two filenames you must know
  • ⭐ buildspec.yml = CodeBuild. Phases: install → pre_build → build → post_build. Must be at the repo root. The artifacts section says what to pass on.
  • ⭐ appspec.yml = CodeDeploy. EC2 lifecycle hooks: BeforeInstall, AfterInstall, ApplicationStart, ValidateService. Lambda hooks: BeforeAllowTraffic, AfterAllowTraffic.
  • Memory hook: Buildspec = Build. Appspec = deploy the App. The exam swaps them to trick you.

4. Elastic Beanstalk and containers

Elastic Beanstalk — you supply only code; AWS creates the EC2 instances, load balancer, and auto-scaling. "Developers shouldn't manage infrastructure" + "traditional web app" = Beanstalk. Its deployment options are the ones in the table above (all-at-once, rolling, rolling with additional batch, immutable, blue/green).

  • Immutable deployment — deploys onto brand-new instances while the old ones keep serving. The safest Beanstalk option, but costly.
  • .ebextensions/ folder holds .config files that customise the environment.
  • ECS — runs containers. EC2 launch type = you manage the servers. Fargate launch type = serverless, no servers. ⭐ "Least operational overhead" + containers = Fargate, always.
  • ECR — the container image registry (AWS's Docker Hub). Login via aws ecr get-login-password.

Django bridge This is all the AWS version of your work. CloudFormation = Django migrations, but for infrastructure. You declare desired state, the tool computes the diff and applies it — and DeletionPolicy: Retain is the same caution you use in a RunPython migration to avoid destroying data. buildspec.yml = your CI file (a GitHub Actions workflow YAML) — same phases: install deps, run tests, build.
