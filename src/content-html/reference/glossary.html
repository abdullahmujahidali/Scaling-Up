Consistency

Consistency
How fresh a read is after a write — whether a later read sees the change. A choice on a spectrum, not a yes/no.
avoid: accuracy, correctness (too vague)
Weak consistency
After a write, a read may never see it — best effort. Good when stale-for-a-moment is harmless and speed matters most.
e.g. video chat, memcached
Eventual consistency
After a write, reads will see it after a short asynchronous delay (often milliseconds). Copies sync in the background.
e.g. DNS, email, a database read replica
avoid: delayed consistency, loose consistency
Strong consistency
After a write, every subsequent read immediately sees it. Copies update synchronously.
e.g. bank balance, classic RDBMS transactions
Synchronous
The write isn't "done" until all copies agree. Drives strong consistency.
Asynchronous
Write now, copy to others later. Drives eventual consistency.

Availability

Availability
Whether the system stays up, especially when a machine fails. Measured as uptime percentage ("nines").
Failover
Keeping a spare or twin server so the system survives one dying.
avoid: fallback, backup (mean other things)
Active–passive failover old: master-slave
One server serves traffic; a standby waits and exchanges a heartbeat. When the heartbeat stops, the standby takes over the IP.
Active–active failover old: master-master
Both servers serve traffic and split load; if one dies the other absorbs it. Everyone (DNS or app code) must know both.
Heartbeat
A regular "still alive?" signal between servers, used to detect failure.
Nines
Shorthand for availability percentage by counting leading nines. 99.9% = three nines; 99.99% = four nines. More nines = less allowed downtime.
Availability in sequence
When a request must pass through multiple components in a chain, their availabilities multiply (A × B), so the total drops below any single one.
Availability in parallel
When redundant components can each serve the request, availability rises: 1 − (1−A)(1−B). A backup only fails if both fail at once.

Scaling & Caching

Load balancer
One front door that spreads incoming requests across many servers, skips unhealthy ones, and removes a single choke point. (Story: the host seating diners across waiters.)
Horizontal scaling
Handling more load by adding more (cheap) servers behind a load balancer. Contrast with vertical scaling.
avoid: scaling out (as jargon)
Vertical scaling
Handling more load by making one server bigger/faster. Simple, but hits a ceiling.
Stateless (server)
A server that keeps no private per-user memory, so any server can handle any request. Shared state (like sessions) lives in a database or shared cache. Required for horizontal scaling behind a load balancer.
Layer 4 vs Layer 7 load balancing
Layer 4 routes by the "envelope" (IP addresses and ports) — fast, doesn't read content. Layer 7 reads the request itself (URL, cookies) and routes smartly — more flexible, more work.
Cache
A small, fast store of copies of frequently used data, kept close to avoid re-doing expensive work. Faster, but copies can go stale. (Story: notes on your desk vs the archive room.)
Cache hit / miss
A hit = the data was in the cache (instant). A miss = it wasn't, so you fetch from the source (slow) and usually store a copy for next time.
Cache-aside lazy loading
The default strategy: app checks the cache, and on a miss reads the database then fills the cache. Simple; first read is slow and data can go stale. (Django's cache framework works this way.)
Write-through
Write to the cache and the database together, so the cache is never stale — at the cost of slightly slower writes.
Cache invalidation
Knowing when a cached copy is out of date and refreshing/removing it. Famously hard. A TTL (timeout) is the simplest form: let a copy go stale after N seconds, then refetch.

Python Internals

GIL Global Interpreter Lock
A single lock that lets only one thread run Python code at a time (in the default build). (Story: one talking stick in a meeting.) Being made optional from Python 3.13–3.14 onward.
CPU-bound
Work limited by processing power (math, parsing, image resize). Threads don't speed it up because of the GIL — use multiple processes for true parallelism.
I/O-bound
Work limited by waiting (network, disk, database). Threads (and async) help a lot: a waiting thread drops the GIL so others run.
Thread vs process
Threads in one process share one GIL (good for I/O-bound work). Separate processes each get their own GIL (good for CPU-bound work — real multi-core use).
async / await
One worker overlapping many I/O waits by switching at each await (cooperative). Very lightweight — scales to thousands of concurrent waits. Helps I/O-bound work only, not CPU. (Story: one cook, many pots.)
Event loop
The single loop that runs async tasks, switching between them at each await. A blocking call (CPU work, sync I/O) freezes it and stalls every task.

Data Integrity

Transaction
A group of database steps treated as all-or-nothing — they all commit, or all roll back. The "A" (atomicity) in ACID. In Django: transaction.atomic().
Race condition
A bug where two operations run at the same time and read-then-write the same data, producing a wrong result (e.g. selling one seat twice).
Lock
Reserves a row so only one transaction can touch it at a time; others wait. Prevents race conditions. In Django: select_for_update(). Overuse risks slowdowns or deadlocks.

Delivery & Structure

DNS Domain Name System
The internet's phone book: translates a name (example.com) into an IP address. Cached with a TTL. An A record maps name→IP; a CNAME maps name→another name.
CDN Content Delivery Network
A global network of servers holding copies of your static files near users, for speed. Push CDN = you upload up front; Pull CDN = it fetches on first request then caches.
Monolith
One application that does everything, deployed as a unit. Simple; can be coupled and scale as a whole. Often the right default.
Microservices
Splitting an app into many small, independently deployable services that talk over the network. Buys independence (deploy/scale/failure isolation); pays in complexity. Service discovery tracks which service is where.
REST
An API style: resources (nouns) at URLs, acted on by a small set of HTTP verbs (GET/POST/PUT/PATCH/DELETE), with self-describing status codes. Exposes data; low coupling. Good for public APIs.
RPC
Calling a named function on a remote server (exposes actions, not resources). Fast, tightly coupled — good for internal service-to-service calls (e.g. gRPC).
Idempotent
Safe to do more than once with the same result (GET, PUT, DELETE are; POST usually isn't). Important for retries — a retried job shouldn't double-charge.
